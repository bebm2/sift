# 持续推进编排（Plan-as-Change）需求分析与落地建议

> 本文是**特性规划**存档：评估一个候选方向、给出分期建议与立项条件，**不代表任何部分已承诺实现**。
> 触发场景：用户已完成 PRD/DESIGN/WBS，希望 Sift 作为主指挥持续推进项目，需要人参与时通过 Issue 找到人。
> 相关边界论述均指向 [PRD](../PRD.md) 对应章节，本文不复制条文。

## 1. 需求拆解

场景里混着两个性质不同的需求：

| # | 需求 | 性质 | 现状 |
|---|------|------|------|
| **R1** | Issue 驱动执行；需要人时系统主动找人（推送 + forge 决策简报 + 一条评论审批） | Sift 核心定位（PRD §1.1、§2.3、A3） | ✅ 产品本体，M7 双 forge 端到端已验证 |
| **R2** | 持续决定「下一步做什么」：读 PRD/DESIGN/WBS → 拆任务 → 派工 → 衔接下一批 | **编排职能** | 无内置机制；但存在已验证的外部解 |

R2 的关键事实：**编排职能今天就有解**。本项目自身的开发就是活例——pi-agent skill 充当主指挥，读 WBS、拆 Issue、打 `agent::*` 标签派工，Sift 做执行层。「外部指挥 + Sift 执行」的分工已被真机验证。因此本分析的问题不是「能不能做到」，而是「**编排该不该收进 Sift 产品内，以及何时**」。

## 2. 候选方案清单

| 方案 | 内容 | 新增机制 |
|------|------|----------|
| **A. 外部指挥模式** | 人 / agent 会话（如 pi-agent skill）负责规划与派工；Sift 纯执行层。规划 Run 可作为普通 docs 类任务跑（Agent 产出计划文档 → Change → 人审） | **零** |
| **B. Plan-as-Change + 确定性 fan-out** | 规划任务产出结构化计划工件（YAML，含子任务清单与依赖图）→ 人审 Change → 合并后 Sift 确定性解析并批量创建子 Issue | `createIssue` 动词、工件 schema、fail-closed 解析器、fan-out 预算 |
| **C. Wave 自动调度** | fan-out 时子 Issue 全部建好但不打触发标签；Reconciler 按依赖图求值（上游 Change 已 merged → `setLabels` 补打触发标签） | 依赖求值一条规则（复用既有动词） |
| **D. 自续环** | 计划末位任务为「起草下一份计划」，合并事件咬合下一周期 | 复用 B/C；预算参数 `max_replans`、计划过期 |
| **E. `sift plan` 命令族** | `status / digest / start / fanout / promote / hold / resume` | CLI 面；写操作全部等效 forge 手动操作 |

方案 B–E 的合规设计要点（若未来立项，必须守住）：

- **A1 合规**：Agent 只产出计划**工件**（提案）；建 Issue、打标签等事实源变更一律由确定性代码执行。朴素版「Agent 自己调 `gh` 开 Issue」明确否决（违反 A1、§9.2、TM1 放大）。
- **Wave 晋升 = 批量打/摘标签**：与人手动操作 forge 严格等效，可信 actor 即本地 CLI 登录身份（§9.2 合规），且人可直接在 forge 界面干预——调度干预获得零成本原生 UI。
- **断链纪律**：所有「继续」静默，所有「停下」可打扰。子任务失败走既有 `failure_review`；计划级失败率熔断暂停整盘；`max_replans` 耗尽 / 计划过期则停并入每日合批摘要；§4.5 反向同步现成收敛。
- **fan-out 解析 fail closed**：任一子任务非法则整体拒绝转人工；幂等键复用 createChange 的 operation marker 模式（需 `findIssueForCreateOperation` 类比件）。

## 3. 客观评估

### 3.1 逐方案判定

| 方案 | 判定 | 理由 |
|------|------|------|
| A 外部指挥 | ✅ **当前正解** | 零产品风险；已被本项目自身开发验证；需求 R2 今天即可满足 |
| B fan-out | 🟡 **价值存疑，暂缓** | 外部指挥用 `gh issue create` 即可等价完成；内置的唯一收益是审计集中，代价是解析器/schema/预算。收益不抵证据门槛 |
| C wave 调度 | 🔴 **超前** | PRD §3.3「任务依赖链自动触发」的立项信号（反复出现「等 A 完再开 B」）**尚未被记录过**；手工打标签成本极低，自动化紧迫性存疑 |
| D 自续环 | 🔴 **最危险的一件** | 纸面优雅，但计划漂移、WBS 中途演化、方向校准全需人介入，实际自主程度远低于纸面；是范围蠕变的藏身之处 |
| E 命令族 | 🔴 **暂缓** | 给尚未以任何形式存在过的实体先做命令面，本末倒置。命名结论存档备查：`sift plan` 独立域优于嵌进 `sift issue`（实体边界：plan 是 Run 之上的编排层；`sift issue` 保持 #963 原案干净） |

### 3.2 两个硬约束（比方案本身更先决）

1. **注意力经济学未过关**。影子门禁未毕业（PRD §5.6 双向不对称阈值需负样本积累）→ 每个 Change 都要人审 → 编排链条只是把「人审 Change」从串行变成并行轰炸。**持续编排的价值主张（减少人的参与）与门禁现实（每个变更都要人看）在 auto_merge 毕业前直接矛盾。** 这是时序问题，不是设计问题。
2. **M7 门禁未闭合**。≥3 并行 Run、P50<60s、手机审批证据均为人工前置项（见 [STATUS](../STATUS.md)）。核心闭环取证完成前设计上一层编排，偏离关键路径。#883（性能 profile）绑定的 M7 并行 Run 片才是当前优先项。

### 3.3 边界合规结论

- 需求 R1/R2 **整体在 PRD 需求边界内**：编排以「用法模式」存在时不触碰任何公理；R2 内置化时，只要守住 §2 的合规设计要点（A1 确定性 fan-out、标签等效操作、断链纪律），与公理体系兼容。
- 但 PRD §1.1「Sift 不是通用任务管理系统」与 §1.2 差异化拷问划出了方向红线：**编排智能必须住在 Agent/prompt/外部指挥里，Sift 内核永远只做筛子与注意力调度**。方案 B–E 的设计均满足此红线（内核零新增智能），违反此红线的任何变体（如 Sift 自主读 WBS 决定下一步）直接否决。

## 4. 建议路线图

| 序 | 动作 | 类型 | 前置/信号 |
|----|------|------|-----------|
| 1 | **闭合 M7 门禁**（≥3 并行 Run、P50、手机审批证据） | 当前关键路径 | — |
| 2 | **写一篇 usage guide**：「外部指挥 + Sift 执行」持续推进模式（commander 会话 + 打标签派工 + Plan-as-Change 手工形态） | `guides/`，即时用户价值 | 无 |
| 3 | **用该模式真跑若干周期并攒信号**：记录「等 A 完开 B」出现频次、每波打扰次数、失败率、计划返工率 | 证据积累（§3.3/§3.4 纪律） | guide 落地 |
| 4 | **#963 按原计划推进**（v1 只读 → v2 起草登记） | 已排期 | 其 v2 顺带落地 `createIssue` forge 动词——整条线唯一有独立价值且已排期的新建件 |
| 5 | 信号齐备后**评估方案 B**（确定性 fan-out），最小实现：schema + 解析 + 预算 | 立项决策点 | 信号：fan-out 手工成本成为真实痛点 |
| 6 | B 落地且有数据后**评估方案 C**（wave 自动求值） | 立项决策点 | 信号：§3.3「等 A 完开 B」高频出现 |
| 7 | D（自续环）、E（`sift plan` 命令族）**保持不承诺** | — | 需 C 的运行数据 + 独立的立项论证 |

## 5. 重启条件（何时回来读本文档）

满足以下任一即可重开评估：

- §3.3「任务依赖链自动触发」立项信号在真实运行中被记录 ≥ 若干次；
- 影子门禁毕业、低风险 auto_merge 生效（解除注意力约束后，编排链条的价值主张才成立）；
- usage guide 模式的 fan-out/衔接手工成本被用户明确反馈为痛点。

## 6. 开放问题（立项时必须回答）

1. **plan 身份锚**：`plan:<id>` 标签 vs 父 Issue 编号串联子任务？倾向标签（forge 原生可筛，人也可用）。
2. **TM6 残余风险**：worktree 内 Agent 同用户身份可直调 `gh` 自建 Issue，无物理保证。缓解 = context 红线 + 事后审计（无 `plan:` 标签的触发摄入即异常信号）；不新增洞，但须如实声明。
3. **计划工件 schema**：子任务字段全集、依赖表达、预算与熔断参数的缺省值来源。
4. **`hold` 语义**：未来自动调度形态下，hold 是否同时抑制 daemon fan-out？倾向是（整盘冻结）。
5. **`sift plan digest` 与 `sift ps` 的边界**：运行态 vs 「要我做什么」，防功能漂移。
6. **计划漂移处置**：WBS 中途变更时，已批准计划的失效与重批准流程。

## 7. 讨论过程纪要（结论的推导链，备查）

1. 直接形态（Sift 自主读 WBS 排程）→ 否决：越界 §1.1/§1.2，且任务事实源是人打标的 Issue。
2. 变通形态（拆任务封装为 Issue）→ 方向成立，但朴素实现（Agent 直接开子 Issue）撞 A1/§9.2/TM1/§5.5 四条边界 → 修正为 Plan-as-Change。
3. 持续串连 → 破局点：「下一步做什么」的决策前置到人批准计划的时刻，运行时只是对已批准 DAG 的确定性求值（等价 CI stage 依赖，不算 LLM 决策）。
4. 命令族 → `sift plan` 独立域（实体边界理由，见 §3.1 E）。
5. 客观重判 → 全部内置机制超前于证据；外部指挥模式是当前正解；路线转为「guide 先行 + 信号驱动立项」（§4）。
