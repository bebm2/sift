## 1. 报告定位

Sift 是一个本地多 Agent 任务编排与门禁中枢（PRD §1.1）。本项目的一个显著特征是：**从 PRD 起草到 M4 门禁闭合，主要由 pi 编排并调用 AI 编码代理推进，同时由人类承担目标设定、流程确认、冲突仲裁与 Human Gate，多来源参与设计评审。** 本文以这个项目为样本，记录这种人机协作形态的工程机制、可观察结果与局限，而不把“AI 驱动”解释成“无人参与”。

报告不评判产品成败（产品价值需 M7 真实链验证，尚未到达），只复盘工程过程。仓库内量化数字绑定基线提交复算；Issue 标签与全局 skill 属可变外部来源，需按附录单独理解。

### 3.3 运行机制：Phase Loop 与多 Agent 编排

本项目"高速落地"的动力学不在单 Agent 一气呵成，而在一套显式的多 Agent 编排协议之上。协议定义于 [`docs/dev/ai-conductor-phase-loop.md`](../dev/ai-conductor-phase-loop.md)，工具链与路由表在全局 skill `~/.cursor/skills/pi-agent`（`SKILL.md` + `references/agent-routing.md`）。

**8 个编号环节（0–7，Phase Loop）**，以 WBS 为唯一主计划权威，协议要求阶段未完成不得跳到下一阶段：

> 0 态势感知 → 1 选定阶段（目标 / 不做清单 / DoD；人工前置单列 **Human Gate**，「Agent 不得伪造」）→ 2 拆 Issue（每个恰好一个 `agent::*` 标签 + 复核建议）→ 3 派 Agent 执行 → 4 阶段门禁（高级 Agent 审核，产出 `reviews/<阶段>-phase-review-<agent>.md`）→ 5 结案回写 WBS → 6 规划下一阶段 → 7 项目完成。

**多 Agent 角色分工**：协议规定总指挥（Conductor）只编排与门禁，不写代码；执行 Agent 按 Issue 的 `agent::*` 标签路由；独立复核 Agent；高级 Agent 做阶段门禁。角色间主要靠 Issue 标签与 worktree 隔离解耦。这里描述的是规定流程；本报告尚未逐 Issue 审计其符合率，不能据此断言每项工作都完整走过所有环节。

**工具链脚本化**：`detect_forge.sh`（自动探测 GitLab/GitHub，不写死 remote）、`run-pi-task.sh --route-issue`（按标签自动选 harness 与模型）、`setup_worktree.sh` / `cleanup_worktree.sh`（worktree 生命周期）、`start_review.sh`（稳定启动审核，避免临时 bash 拼盘）。默认流水线是 `route → worktree → 实施 → 复核 → MR → 合并 → 清理`；阶段报告中仍可见部分 PR 无 review/comment，说明独立核验有时由合并后的定向复审或阶段门禁补足。

**多模型路由**：`agent-routing.md` 的能力目录覆盖 6 家厂商、12 个 `agent::*` 标签，按 Issue 性质（CI / 视觉 / 编码 / 长上下文 / 深推理）选型；这证明“可路由范围”，不证明 12 个标签都被实际使用。以当前 GitHub 标签回看截止点前创建的 188 个 Issue，实际出现 6 个 slug：gpt-5.6-terra 80、gpt-5.6-sol 58、gpt-5.6-luna 29、glm-5.2 17、kimi-k3 3、deepseek-v4-pro 1，即约 4 个模型来源，且 GPT-5.6 系列约占 89%。标签只证明派工意图；若要证明最终执行模型，还需保存 conductor 运行记录。

**审修闭环（核心质量机制）**：实施(A) → 审核(R) 只出「关闭包」（不改生产代码、不自审通过）→ 返工实施(B)。规则显式对抗单一模型盲点：证据 / 契约 / 边界问题**必须 switch**（换编码向 agent，≠ 审核人）；同类 P1 ≥2 轮未关强制换人或拆单；同 agent 实施 ≥3 轮失败**升级到换模型 / 拆单 / Human Gate**。

这个机制解释了前述若干可观察现象：

- WBS 因【5】强制回写而具有统一聚合入口，提高了可追溯性；但它仍是流程内自报数据，需由门禁证据交叉验证，不能仅因协议存在就视为独立可信；
- `m3/m4-phase-gate-rereview-*` 系列是【4】门禁的产物；
- Human Gate 是**设计内的显式边界**（【1】明令不得伪造，审修闭环的升级终点），框定了 §7.2/§7.3 的局限判断——那是流程承认的卡点，不是疏漏；
- 开发流程的 worktree 隔离纪律（「禁止主工作区改代码」）呼应了产品 A5 隔离公理，可视为流程层面的“吃自己的狗粮”；它不是与产品运行时隔离同等级的结构保证。

**实践意义**：本案不是「一个 AI 从头写到尾」，而是**人类定义目标、编排协议与升级边界，AI 在协议内承担大部分分析、实施与复审**的形态。Phase Loop 把「什么由 AI 做、什么卡在人类」写成显式环节与升级路径；其可复用价值成立，但实际符合率仍需另行量化。

## 4. AI Agent 工程实践的特征

本节归纳本项目过程中可识别的、具有 AI Agent 实践特征的工程模式。每条给出**可观察证据**，不臆断意图。

### 4.1 文档即契约：与 AI 代理的接口

[`docs/README.md`](../README.md) 显式定义了"与 AI 代理的接口"：文档头 `status` 字段机器可读，代理据此判断可信度；`summary` 供渐进披露；按任务类型给"默认上下文集"表，**禁止全量加载 `docs/`**。根目录 [`AGENTS.md`](../../AGENTS.md) 只放指针与规则，不放内容。

证据：`docs/README.md`「与 AI 代理的接口」「上下文预算」两节；除按约定无需 front matter 的 `reviews/` 外，子目录文档均有标准文件头；`status: done/abandoned/superseded` 的文档被默认上下文过滤。

**实践意义**：front matter、docs-as-code 与单一事实源并非 AI 时代才出现；本案的新变化是文档还作为代理的**上下文管理协议**。`status` 字段成为上下文路由信号，降低有限上下文被无关历史污染的风险。

### 4.2 评审与实施的多模型分层

需区分两个易混的量：**评审者署名**（reviews 文件名）与**实施者路由**（Issue 的 `agent::*` 标签）。两者分布不同，不可合并讨论：

| 阶段 | 评审者来源 | 实施者来源 |
|------|-----------|-----------|
| PRD（7 份评审） | 文件署名 consultant × 6 + third-party × 1；仓库未记录其模型/人员独立性 | 人类执笔 |
| DESIGN（18 份评审） | kimi-k3 × 6 + hex（人类）× 5 + codex × 3 + glm-5.2 × 2 + gpt-5.6-sol × 2（**5 来源交叉**） | 人类执笔 |
| M1–M5 实现与字段审定 | 评审文件绝大多数署 pi-gpt-5.6-sol；全库 105 份中有 74 份使用该署名（**评审集中**） | Issue 标签实际出现 6 个 slug、约 4 个模型来源，且约 89% 为 GPT-5.6 系列；标签不等于最终执行证明 |

**设计期是多来源模型 + 人类交叉**。DESIGN 的 4 轮阻断改版里，D0.2→D0.3 由 kimi-k3 判「不进 WBS」（其余通过）、D0.4→D0.5 由 codex/glm/kimi 三份连续阻断——不同来源的意见确实形成了交叉否决。但文件署名只能证明评审来源标识，不能证明统计独立性或无共享提示偏差。

**实现与评审都存在集中度风险**。实现期路由并非单模型，但绝大多数 Issue 标签仍落在 GPT-5.6 系列；评审文件又高度集中于 gpt-5.6-sol。Phase Loop 的审修闭环（§3.3）通过“审核不改生产代码、返工换编码向 agent、失败升级 Human Gate”降低同一执行者自我背书的风险，但无法消除同模型族的系统性偏好。

**实践意义**：本案支持“按阶段与角色分层路由值得继续验证”，尚不足以证明“广泛异构多模型实施优于单模型”。后续应同时记录路由标签、实际执行模型、复核模型与人工介入，才能评估分层收益。

### 4.3 结构性保证优先于纪律性保证

DESIGN §2.3 原则 1：**“想禁止的事，做法是让实现它的函数不存在，而不是写进注释。”** M1–M4 代码把多项原则落实为不同层级的保证，但并非全部都是类型级约束：

| 禁止的行为 | 主要保证层级 |
|-----------|-------------|
| 绕过状态机改 Run 状态 | 包封装：`transition()` 私有，未提供通用 `UpdateRun` API；仍需测试/审计防止包内新增旁路 |
| LLM 决定 severity | API/类型：`BaseSeverity` 函数签名不接收外部或 LLM 输入 |
| Agent 读 worktree 内策略 | 组装边界 + git argv：策略从 base 读，Sift git 调用强制 `-c core.hooksPath=/dev/null` |
| 同一 permit spawn 两次 Agent | wrapper-local `PermitGate` + 持久 handoff/CAS 协议 + 崩溃测试共同保证 |
| actor 缺失的事件进入领域层 | 运行时边界校验：`Actor` 仍是可为空的 `string`，adapter/contract suite 对空 actor fail closed，并非类型系统直接禁止 |

**实践意义**：应把保证明确区分为类型/API、包封装、持久化约束、运行时验证与自动化证据。AI Agent 容易只补注释；本项目较多地消除了旁路，但“结构保证”仍应逐项说明强度，不能一概等同于类型系统。

### 4.4 高密度评审 + 对账节作为质量机制

评审密度：105 份评审 / 2.3 天，其中 DESIGN 单文档 18 轮、M5 command spec 9 轮 rereview。DESIGN §14.4–§14.14 的 **11 个相关对账子节**逐条记录设计评审的编号、级别、发现、处置与落点，并对“本表所列项全部采纳，无驳回”作了范围限定（§14.5）。实现期评审主要回写 WBS 和对应规格，不是所有评审都进入 DESIGN 正文。

对账节还记录了**承认错误的修正**：§14.12 明确"曾把一项独立自查的问题错误归为 review-15 的发现，并在 PRD/CHANGELOG 复制该归因；这是事实性错误，现统一更正"。

**实践意义**：评审密度本身不等于质量；更有价值的是按文档权威边界维护“评审→处置→落点”的可追溯三元组。它提高了复核性，但仍需结合首轮通过率、P1 关闭轮数和真实缺陷结果判断评审效能。

### 4.5 引用不复制：单一事实源

[`docs/README.md`](../README.md) 明令"同一份事实只写一次，其余地方用相对链接引用"，理由是"AI 代理对矛盾上下文的容错很差，重复内容必然漂移"。DESIGN 全文坚持：字段级契约下沉 `specs/`、决策取舍下沉 `decisions/`、正文只讲结构与理由并链接引用。

证据：DESIGN §15「派生文档清单」显式列出每份 spec/ADR 承接的内容；本报告自身也遵循该纪律。

**实践意义**：人与代理都会受重复事实漂移影响；代理在有限上下文和自动执行场景中更容易把矛盾直接转化为实现错误。因此“引用不复制”在 AI Agent 工程里更接近正确性约束，而不只是风格偏好。

### 5.2 设计约束的落点与偏离

M1–M4 的阶段评审与测试为多项核心约束提供了可复核落点：唯一转移入口、Gate 纯函数、severity 确定性、策略从 base 读、actor fail closed、`spawning` 不可换 owner等。但这些保证分属 API、包封装、运行时校验、持久化协议和测试，不宜概括为“均由类型/签名锁死”，也不能由当前证据推出“无未知结构性偏离”。

一个有代表性的 DESIGN→实现偏离是单 ticker 未接 DESIGN §6.1 三组步频；代码在截止前已调整，但[截止点定向评审](../reviews/2026-07-29-m5-scheduler-wakeup-302-pi-gpt-5.6-sol.md)因 production-path 自动化证据不足判 **FAIL**。M4 多轮门禁还发现了 Gate 纵向接线、merge worker、reverse-sync、marker recovery 等集成缺口，说明设计收敛显著降低了概念返工，却没有消除生产接线与证据闭合成本。

**实践意义**：本案观察到“组件代码快速落地、集成门禁多轮收敛”的组合，而不是“实现只是翻译”。是否兼顾速度与质量，仍需以 M7 真实链、逃逸缺陷和长期维护数据验证。

## 6. 卡点

本节归纳从 PRD 到 M4 完成整条时间线上的摩擦分布与根因。**「卡点」口径是迫使返工 / 改版的阻断**（评审结论为「不进 WBS / 阻断 / P1」或 DESIGN 版本因评审递增），不含顺流推进的正常评审。它与“工作量”不同——卡点的标志是**需要多轮迭代才能收敛**。

时间预算已在 §3.1 给出：设计期（25 份 PRD/DESIGN 评审）以契约拉锯为主，07-29 则同时出现高提交密度和密集门禁返工。**概念摩擦主要前置，但集成与证据摩擦明显后置**；不能仅用提交速度推出实现已退化为机械翻译。

### 6.1 设计阶段的阻断轮次

DESIGN 从 D0.1 到 D0.10（active）经历 **18 轮评审**，其中 **4 轮为阻断级**（评审结论迫使版本递增并重做相关章节）：

| 改版 | 驱动评审 | P1 核心 | 主题聚类 |
|------|---------|---------|----------|
| D0.2 → D0.3 | review-05（四份复审中唯一判「不进 WBS」；DESIGN §14.6） | Gate 缓存键遗漏可变输入 / claim 无可实现获取路径 / Change 创建证据不足 | 幂等与证据 |
| D0.4 → D0.5 | review-09~12 连续四份阻断（DESIGN §14.8；其中 [review-10](../reviews/2026-07-27-design-review-kimi-k3-03.md)、[review-11](../reviews/2026-07-27-design-review-codex-02.md)、[review-12](../reviews/2026-07-27-design-review-glm-5.2-02.md) 文件已确认） | 两次同凭据 `claim:confirm` 无法区分重放 / `running` 在真实 spawn 前落库 | **spawn 交接协议** |
| D0.6 → D0.7 | [review-14](../reviews/2026-07-28-design-review-codex-03.md) | 进入人工态后迟到的合法 `started` 无线性化规则 | 事实与决定的仲裁 |
| D0.9 → D0.10 | [review-16](../reviews/2026-07-28-design-review-gpt-5.6-sol-01.md) | merge 缺 expected-head CAS / `startup_stall` 终局矛盾 / retry 探测缺原子收敛 | 副作用线性化 |

> review-05 的文件归属 DESIGN §14.6 未明确标注（该节警告「编号需要提防」），故不硬链文件，统一以 DESIGN 章节号为追溯入口。完整逐条处置见 DESIGN §14.5–14.14。

实现阶段的摩擦也不均匀：

| 里程碑 | 评审数 | 相对摩擦 |
|--------|--------|---------|
| M1 骨架 | 3 | 低 |
| M2 Forge/Intake | 5 | 低 |
| **M3 Runtime** | **10** | **高：恢复与并发安全** |
| **M4 Gate/Ledger** | **7** | **高：生产接线与证据闭合** |

M3 的评审数最高，主要摩擦与恢复矩阵同源（§6.2）；M4 虽少 3 份，但经历多次阶段门禁 FAIL，不能归为低摩擦。两者分别代表“协议/并发正确性”和“纵向集成/证据充分性”两类成本。

### 6.2 根因一：spawn handoff / attempt 生命周期（主导技术难点）

**§8.4（attempt spawn handoff）+ §10.1（恢复矩阵）这一对章节，单独吞噬了设计阶段 3 轮阻断改版（D0.4→D0.5、D0.6→D0.7、并部分驱动 D0.9→D0.10）+ ADR-010 / ADR-012 / ADR-013 三份决策 + M3 实现期半数评审。** 它是整个项目最大的卡点。

为什么难——三件事在同一处叠加，且无法分层降级：

1. **单写入者保证**：一个 attempt 在任一时刻至多一个存活执行体写同一 worktree（否则 Agent 并行写坏仓库）。
2. **崩溃恢复**：daemon/wrapper 随时可能被 `kill -9`，恢复后必须能判断“上一次 spawn 到底成没成”。
3. **一次性语义**：spawn 这个动作“重复执行 = 两个进程并行写同一 worktree”，不能靠事后幂等收敛。

难点在于 **OS `spawn` 不消费 fencing token**——纯逻辑层的 CAS / 代次校验挡不住“校验通过后、spawn 前”这个窗口。这逼出了 `spawning` 这个不可换代的中间态、一次性 spawn permit、受控终止流程、以及 `attempt_resolution` marker 的事实 / 决定仲裁。每一层都是为了堵前一层留下的窗口。

M3 实现期的高摩擦是这个深坑的直接外溢：设计文档里“另一侧留白”的债（§6.3）在实现 + 测试逐行兑现时继续暴露，靠实现期复审补。

### 6.3 根因二：「补一侧、漏一侧」元模式

这是最值得记录的一条——**不是某个技术点，而是评审方法本身被项目自己识别、但重复发生了至少三次的反模式**。

DESIGN §14.10 与 §14.11 原文明确记录：

> 「D0.5/D0.6 把新纪律写在了评审压力所在的那个阶段与那个后端上，没有推到不变式的全部边界。」
> 「这已是第三次：新机制补在被审的那一侧，另一侧留白。」

三次的轨迹：

| 次 | 补在哪 | 漏在哪 | 代价 |
|----|--------|--------|------|
| 1 | `spawning` 窗口补在 `process` 后端 | `tmux` 后端下观测原语失效（R13-N1，DESIGN §14.10） | 一次拓扑裁决 |
| 2 | 受控终止流程只补在 `spawning` | `running` 阶段的 `orphaned` 漏（§14.10 自查） | 一轮自查改版 |
| 3 | 人工态只定义“怎么进” | “进去之后迟到事实怎么办”没定义（[review-14](../reviews/2026-07-28-design-review-codex-03.md) P1） | 一轮阻断改版 |

**机制**：评审是有焦点的。当一份评审盯住某一侧（某个阶段、某个后端、某条路径），修订自然把那一侧补严；而不变式的**全部边界**没人盯，下一轮评审才发现另一侧的洞。每次代价是一轮完整改版。

这条之所以是“元卡点”而非偶发失误：它**不在任何单一技术决策的范围内**，因此没有任何一份 ADR 或 spec 能单独闭合它——它只能靠评审纪律（每次补机制时强制枚举不变式的全部边界）缓解，而纪律性保证按 DESIGN §2.3 原则 1 本就是最弱的保证形式。

### 6.4 根因三：副作用线性化（次级）

D0.2→D0.3 与 D0.9→D0.10 两轮阻断都部分落在 outbox 的逐类投递语义上（Gate 缓存键、Change marker 全状态搜索、merge expected-head CAS）。难度中等，但因与 §6.2 的恢复矩阵交织（agent 启动是表里唯一“重复执行有破坏性”的副作用），反复被牵连进改版。已由 [ADR-003](../decisions/003-transactional-outbox.md) / [ADR-011](../decisions/011-merge-requires-expected-head-cas.md) 闭合。

### 6.5 为什么组件落地快、阶段门禁仍反复

M1 / M2 相对顺流；M3 在恢复安全上高摩擦，M4 则在生产纵向链和证据充分性上连续返工。设计阶段确实提前关闭了大量概念歧义，使组件实现速度很高；但组件 API 存在不等于生产链接通，测试存在也不等于覆盖关闭标尺。

更准确的结论是：**前置设计降低了“做错机制”的返工，阶段门禁继续承担“没有接到生产路径”与“证据无法区分正确实现和偶然通过”的发现责任。** 这与 DESIGN“难度在约束相互作用”的判断一致，同时否定了“想清楚后实现只剩翻译”的过强表述。

### 6.6 对后续工作的影响

**M5 正在复现契约拉锯。** 字段规格已积累 33 份评审；同时 #302 scheduler 前置实现已经开始，截止点因 production-path 证据不足未通过复审。Command 涉及鉴权、nonce、options、回执、Ledger 同事务与 `startup_stall` 两段式，推断仍是后续高风险区。DESIGN §10.1 所需的统一仲裁函数 `ResolveAttemptRace` 已存在，`claim:started`、恢复补 started、迟到 `result.json` 三个入口已接；M5 的具体抓手应是**接通第四个 Interrupt/Command 入口，并用同一组交错测试证明四入口语义一致**，而不是重新实现函数。

M3 中未勾选的完整恢复矩阵、确认消失后的生产资格与 hooks 自动复核并非都应统称“技术债”：双后端矩阵按计划在 M6 闭合，真实 Agent/version 资格在 M7 验证。M6 开始前应核对 process 侧可复用前置是否齐全，并在 M6 内以 process/tmux 同套矩阵最终收敛；不得把计划中的 M6/M7 范围提前描述为 M3 已完成，也不应要求在 M5 中虚假勾选。

M7 预计是速度回归点，但那主要来自真实环境、人工验收与外部系统不确定性，当前数据还不能估算幅度。

## 7. 局限与风险

本节是本案作为 AI Agent 实践样本的**诚实边界声明**（呼应 DESIGN 原则 5「诚实优于漂亮」）。

### 7.1 实现路由与评审都高度集中

实现期不是严格单模型，但实际 Issue 标签约 89% 落在 GPT-5.6 系列，评审文件又高度集中于 gpt-5.6-sol。审修闭环的职责隔离（审核不写代码、返工换编码向 agent，§3.3）能降低同一执行者自我确认，却挡不住同模型族对代码模式、证据充分性或规格措辞的共同偏好。**缓解建议**：关键阶段门禁引入异构模型或人类抽查，并保存“路由标签→实际执行模型→复核模型”的运行记录。

### 7.2 真实环境验证完全缺位

现有证据并非只有单元测试：项目已有 fake/fixture 契约测试、真实子进程与 process wrapper 集成、崩溃注入、`SIGSTOP`、race 和 production wiring 测试。缺失的是**真实外部环境**：PRD §10.1 的真实 GitHub/GitLab 项目链、真实 Agent 闭环、手机端审批、干净机安装均安排在 M7，截止点尚未执行。测试骨架质量高 ≠ 产品可用；Phase Loop【1】已将此类人工前置列为 Human Gate（“Agent 不得伪造”），故这是设计内边界，但仍可能暴露当前测试未建模的问题。

### 7.3 可持续性未经验证

07-29 在约 20.5 小时活动窗口内产生 286 次提交，属于冲刺态。M5（44 项实现）+ M6（故障矩阵）+ M7（真实 PoC，需人工）+ M8（发布）还有 90 个未勾选 checklist，其中 M7 依赖真实环境与人工验收，无法仅靠 agent 闭环按当前节奏推进；当前速度不可直接外推。

### 7.4 评审密度的成本

105 份评审的 token/API 成本、机器时和人工仲裁时长尚未记录，不能称为“近乎免费”。多来源交叉还有协调成本：DESIGN 多份复审需要人类选择权威结论、处理编号冲突（DESIGN §14.6 自述“编号需要提防”）。在缺少成本数据前，只能确认该流程在本次冲刺中可运行，不能判断其经济性或可移植性。

### 7.5 样本与因果边界

本报告只有一个项目、一个超短冲刺窗口，没有人类团队、单模型流程或弱文档流程作为对照组；提交、Issue 标签与评审数量也只是过程代理指标。因此“前置设计、结构约束、对账评审与高质量结果相关”可以作为本案观察，尚不能证明因果关系或外推到其他技术栈、团队规模与长期维护阶段。

## 8. 可复用的经验

按"可直接迁移到其他 AI Agent 软件工程项目"的成熟度排序：

1. **文档即上下文协议**（§4.1）：`status` 字段 + 渐进披露 + 按任务类型的默认上下文集表。低成本、高收益，任何 AI Agent 项目可立即采用。见 [`docs/README.md`](../README.md)。

2. **按角色分层路由，并记录实际执行证据**（§3.3/§4.2）：设计期使用多来源交叉，实施期按 `agent::*` 路由，审核与实施职责分离；同时记录实际模型和集中度，避免把能力目录或标签当成已执行事实。

3. **结构性保证翻译清单**（§4.3）：每条设计原则在代码评审时要求给出对应的保证层级（类型/API、包封装、持久化约束、运行时验证、自动化证据），而非只给注释。把 DESIGN §2.3 原则 1 变成可核对项。

4. **评审对账三元组**（§4.4）：评审→处置→落点写回对应权威文档（设计问题回 DESIGN，进度回 WBS，字段契约回 spec），外加“承认错误”的修正机制。

5. **引用不复制**（§4.5）：作为正确性约束写入文档纪律，针对 AI 代理的上下文容错特性。

6. **诚实声明未闭合边界**（§7、DESIGN §9.1 TM6）：不把"某条路径上没有能力"写成"系统没有这个能力"。doctor 如实报 `unsafe-local`。这套做法可直接复用。

7. **审修闭环分离职责**（§3.3）：审核只出“关闭包”不改代码、返工更换编码向 agent、失败升级到 Human Gate。它能减少自我背书，但是否真正换了模型应由运行记录证明。规则目前部分位于可变的 `~/.cursor/skills/pi-agent`，复用前应记录 skill 版本或 digest。

8. **编排协议脚本化并审计符合率**（§3.3）：Phase Loop 配套 `detect_forge` / `route-issue` / `setup_worktree` / `start_review` 等脚本，把派工、隔离和审核固化为工具链；同时应统计多少 Issue 实际走完全流程及例外原因，避免把协议文本当成执行证据。

9. **固定统计基线**：报告绑定 commit SHA、时区和外部数据快照；仓库指标与 GitHub/全局 skill 指标分开声明，避免“当前状态”持续漂移。

## 9. 结论

Sift 项目在约 2.3 天内推进到 M4 限定范围阶段门禁闭合，基线包含约 2 万行非测试 Go 物理行、约 1.4 万行测试 Go 物理行、13 份 ADR、12 份 spec 与 105 份评审存档。多项核心设计约束已有代码和测试落点，同时 M3/M4 多轮门禁也暴露了恢复、生产接线和证据充分性缺口。

作为单一 AI Agent 软件工程样本，它呈现的形态可概括为：**多来源交叉的设计 → 高度集中但非单一的模型路由 → 分层结构保证 → 职责隔离的审修闭环与可追溯评审对账。** 数据显示这套组合与快速组件落地、密集缺陷闭环同时出现；没有对照组，不能据此断言因果关系。

局限同样清晰：**实施路由和评审都集中于 GPT-5.6 系列、实际执行模型证据不完整、真实环境验证缺位、成本与人工投入未量化、速度不可向 M7 外推。** 在 M7 真实链跑通之前，本案支持的是“AI Agent 在明确协议和人类边界下能快速完成大量设计、实现与验证工作”，尚未证明能独立交付经真实环境验证的产品。

一句话：**本案值得关注的不是提交峰值，而是文档上下文协议、结构约束、Human Gate 与证据门禁如何共同限制 AI 的错误传播；其效果仍需真实链、成本和长期维护数据验证。**
