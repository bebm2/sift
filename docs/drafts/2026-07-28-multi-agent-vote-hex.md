# 多 Agent 设计评审与投票场景 — 范围讨论

> 来源：与项目所有者的设计讨论。讨论串围绕一个特定场景展开：
> **设计任务：Agent A 主写 → Agent B/C/D 评审 → Agent A 修订 → 再评审 → 多轮 → 多数通过 → 交 Human 终审**
> 最终结论：在 Sift 范围外，作为独立项目通过 Agent 协议接入。

---

## 1. 原始场景

> 我有一个设计任务需要由一个 Agent 负责主写，然后由其他 Agent 评审输出意见，然后再修订，继续评审，这样持续多轮，直到多数 Agent（可由任务设定要求）这个设计任务才通过，交给 Human 审批。

## 2. 与 PRD 的逐项对照

| 维度 | 当前 PRD | 用户描述的场景 | 是否匹配 |
|------|----------|---------------|---------|
| Agent 拓扑 | 单 Agent 执行 | 多 Agent（主写 + 评审团） | ❌ |
| 流程 | 线性管道（§6） | 多轮迭代循环 | ❌ |
| 审批主体 | 人（HITL） | Agent 投票 → 人终审 | ❌ |
| 状态模型 | 5 态，无 `in_review`（§4.1） | 需 `draft→review→revise→vote→…` 循环 | ❌ |
| `design_approval`（§4.3） | 单次开工前审批，人确认 | 多轮 Agent 设计评审 | ❌ |
| 核心价值主张（§1.2） | 筛子 + 注意力调度器 | Agent 协调器 | ❌ |

### 2.1 关键不匹配细节

- **状态机不支持多轮**：`waiting_human` 是一次性检查点，收敛方向单一；§4.1 允许的「迟到的执行事实」回边不构成可重复的修订循环。
- **无多 Agent 协调机制**：Brain（§5.3 T2）只做一次分派，不分「主写 vs 评审」角色；Agent 间不通信。
- **无多数投票逻辑**：审批链路是人的一条评论（§7.1），不存在「N 个 Agent 投票，过阈值算通过」。
- **零自建 UI 原则（§7）的约束**：多轮评审需要追踪版本、汇总观点分歧，无法在 forge 评论上表达为 ≤4 个选项（A6）。

## 3. 架构洞察：虚拟 Agent 包装器

> 经过讨论，识别出一个干净的架构解：**创建一个「虚拟 Agent」，它在内部是一个多 Agent 团队，对外暴露标准 Agent 协议，从而作为普通 Agent 接入 Sift。**

### 3.1 契约图

```
Sift
 └─ Run[worktree]
     └─ 虚拟 Agent（独立包装器）
          ├─ Agent A（主写设计）
          ├─ Agent B（评审）
          ├─ Agent C（评审）
          ├─ Agent D（评审）
          └─ 内部逻辑：迭代编排 + 多数投票
```

### 3.2 协议映射

| Sift Agent 协议节点 | 虚拟 Agent 的内部实现 |
|---------------------|---------------------|
| 接收 Task Spec | 按 specs 分派给主写 Agent |
| `sift report` | 报告当前轮次、阶段、子 Agent 状态 |
| 提交分支（Sift 检测） | 内部多轮迭代完成 → 最终设计落盘 → 提交 |
| 退出码（Layer 2 裁定） | 0 = 设计通过等待 Human；非 0 = 内部失败 |

### 3.3 为什么这个解是干净的

| 优点 | 说明 |
|------|------|
| Sift 不需改一行 | 状态机、Gate、注意力配额、forge 集成全不变 |
| 职责分离清晰 | Sift 管筛子与注意力；虚拟 Agent 管多 Agent 协调 |
| 独立演进 | 可有自己的配置（子 Agent 列表、投票阈值、最大轮次），与 Sift 策略不耦合 |
| 复用现成隔离 | worktree 隔离、双层上报、退出码裁定全是现成的 |
| 验证 Sift 协议质量 | 虚拟 Agent 是第三方实现，协议若隐含倾斜会最早暴露 |

### 3.4 边界提醒

- `code_review` 的 `min_modality: visual`（§4.3）针对人类评审，不约束 Agent 间评审
- 超时设计需两层：Sift 侧 Run 超时 + 虚拟 Agent 内每轮子超时
- `sift report` 限流（§5.8）适用于虚拟 Agent 总量，内部所有子 Agent 共享配额
- TM6（worktree 外无物理保证，§9.1）同样适用，不因层数增加而放大或缩小

## 4. 现有多 Agent 工具调研

| 工具 | 原生支持多 Agent 团队？ | 如何用于虚拟 Agent |
|------|-----------------------|-------------------|
| **Pi** | ❌ 单 Agent Harness | 可作为评审子 Agent：`pi -p "审阅以下设计…"` |
| **Claude Code** | ❌ 单 Agent CLI | 可作为主写或评审子 Agent：`claude -p "…"` |
| **OpenCode** | ❌ 单 Agent CLI | 同，可脚本化调用 |
| 其他 | — | 本质相同：所有工具都提供了进程级可编程接口（`-p` 管道模式），可以被外层编排脚本多次调用来模拟多 Agent 流程 |

**结论：无需等待任一本机 Agent 支持多 Agent 团队。** 一个几百行的编排包装器即可组装出「虚拟 Agent」，对外以标准 Sift Agent 进程形态呈现。

### 4.1 包装器伪代码

```
虚拟 Agent（入口点）

  1. 读取 Task Spec（来自 Sift 的环境变量或文件）
  2. 循环（最多 N 轮）:
     a. 调主写 Agent: claude -p "作为设计者，按 specs 产出 V{i}" → 写文件
     b. 并发调评审 Agent（Pi/Claude Code/其他各一次）:
        "作为评审人，审阅 V{i}，列出问题"
     c. 汇总评审意见
     d. if 通过票数 ≥ 阈值 → break
     e. 调主写 Agent: claude -p "根据以下意见修订 V{i}，产出 V{i+1}"
  3. 提交分支到 origin（Sift 会检测到）
  4. 退出码 0（成功）/ 非0（内部失败，如超轮次或子 Agent 异常）
```

## 5. 范围裁定

| 问题 | 结论 |
|------|------|
| 虚拟 Agent 是否属于 Sift 本项目？ | **否**。独立项目、独立仓库、独立发布 |
| Sift 需要为它改什么？ | **什么都不改**。Agent 协议保持现在的通用契约 |
| 是否有风险限制它接入？ | 需确保 Agent 注册/配置不把「只有一个 Agent」的假设写死 |
| V0 如何对待？ | V0 聚焦：单 Agent × 双平台 × 门禁 × 注意力配额。虚拟 Agent 是 V0 后的独立生态 |
| 往后发展？ | 虚拟 Agent 在实践中成熟后，可考虑作为 Sift 的**官方推荐配套**，但仍独立 |

### 5.1 裁定依据

- **PRD §1.2 核心价值主张**：Sift 卖筛子，不是卖 Agent 协调器
- **PRD §3.2 V0 不做**：「嵌入式自研 coding agent 框架」不做。虚拟 Agent 虽不是框架，但属同类方向——把 Agent 协调逻辑往 Sift 内部推
- **PRD §1.4 A4**：最快闭环优先。V0 应在 1 Agent × 1 项目跑通，不摊开做多 Agent
- **PRD §3.4**：PoC 先验管道通、门禁会拦、双平台对称、注意力配额管用，这些皆不依赖多 Agent 编排
