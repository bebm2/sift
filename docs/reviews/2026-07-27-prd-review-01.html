差异化 01

门禁 ≠ 又一个 Agent

确定性代码把关，LLM 只出「建议」。状态转移、门禁、合并全由代码执行，不靠模型「拍板」。

差异化 02

Forge 即唯一信道

gh/glab CLI 作为人-机唯一接口，零凭据管理，GitHub/GitLab 双平台对称。

差异化 03

零自建 UI

人驻留在 forge 的评论/标签里，手机 App = 全功能审批终端；daemon 零开放端口。

设计亮点 · 3 支柱

为什么这套设计 立得住

A1 无权柄原则

LLM 只有发声权

模型只产出建议；所有状态转移、门禁、合并由确定性代码执行。可控、可审计、可回放。

Forge 抽象

双平台对称

gh/glab 作为唯一信道，行为归一；零凭据管理，部署面极小。

零自建 UI

寄生式人机界面

人留在 forge 评论/标签；手机 = 审批终端；daemon 不暴露任何端口。

风险与缺口 · 2×2

真正要盯的 4 件事

高影响 · 内部可控

① 门禁可信度

auto_merge 前必须靠 Shadow Gate 积累「预审命中率」证据，否则不敢自动合。

高影响 · 外部依赖

② 双平台一致性

GitHub / GitLab API 差异会悄悄导致行为漂移，需抽象层兜底。

中影响 · 内部

③ 注意力稀释

中断太多反而淹没人。需严格 ≤4 互斥选项 + 频率预算。

中影响 · 可观测

④ 配置漂移

多 repo 策略不一致会埋雷，需「策略即代码」+ 集中校验。

开放问题 & 建议 · 6 行

把 PRD 的问号，变成动作

#开放问题（来自 PRD）建议动作
1Shadow Gate 准确率到多少才开 auto_merge？先跑 50 次 PR 双盲，目标预审命中 ≥95% 再启用。
2双平台 API 差异如何归一？抽象 Forge Adapter 层，维护差异矩阵与回归用例。
3中断频率上限怎么定？引入「注意力预算」，给每日中断配额与降级策略。
4多 repo 策略如何保持一致？策略即代码，中央模板 + CI 校验，禁止逐仓漂移。
5失败如何优雅回退？T6 失败分流三态：自动重试 / 转人工 / 安全放弃。
6Brain 自我标定频率？周级离线回放 + 人工抽检，量化偏差再校准。
