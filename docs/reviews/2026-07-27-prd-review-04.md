## 总评

三审我列的 5 条 gap（A–E）+ 一个行文小拧，**这一版全部接住**。其中 A（actor 动词）、B（反向同步 actor 校验）、C（critical 熔断）、D（PRD/DESIGN 边界）、E（`sift speak` 拒 visual）——一个没漏。而且 A/B 两条作者**没有照抄我的修法，而是按更深的原理解了**：

- 三审 B 我说「§4.5 每条挂 actor 校验」。作者没照做，而是把反向同步拆成**事实 vs 指令**——Issue 关闭 / Change 合并是 forge 事实，挂 actor 校验反而会让 Sift 与事实源脱同步（fail closed 在这里比放行更糟）；只有「触发标签移除」这种可逆控制面信号才挂鉴权。这比我的建议对。
- 三审 A 我说「补 `getEventActor`」。作者补了 `listLabelEvents(target, since)` 返回 actor + 评论动词强制返回 `author` + 一条「actor 是契约不是实现细节」的 callout。更系统。

到这版，我的评审角色从「挑设计错」退化成「挑边角一致性 + 确认作者没自己前后打架」。这是好事。

**这一版真正的新主角：§9.1 TM6 ——「worktree 之外的一切都不受保护」。**

## 作者这一次长出来的硬货（该给的 credit）

### TM6：诚实的未闭合边界声明
这是整份 PRD 到目前为止最成熟的一段。作者承认：worktree 是 git 层组织方式，**不是 OS 层沙箱**；Agent 以当前用户身份跑在本机，所以 `~/.sift/`、已登录的 `gh`/`glab`、共享 `.git` 的 hooks、其他 Run 的 worktree，全都不在护栏覆盖内。

并**主动修正了两处过度声明**（这种 self-correction 比任何设计都值钱）：
1. 「Agent 不持有 forge 凭证」→ 改口为「Sift 不**主动传**凭证，不是 Agent 取不到」——这是选 `gh`/`glab` 集成通道付的代价，§5.2 的「零凭证管理」收益现在有了安全脚注。
2. A5「物理保证」→ 限定为「仅 worktree 内相互隔离」，不保证「Agent 无法触碰系统自身」。

且这两条修正**贯穿全文档一致**：A5 正文（line 70）、TM1（line 648）、§5.2 安全脚注（line 278）、§9.3 安全行（line 706）、§9.1 末尾「Agent 能力边界（V0 实际状态）」全部对齐成「约定与缓解，非强制」。没有一句还在偷偷声称「安全」。

配套：§3.3 Backlog「更强隔离」立项信号改为「TM6 是结构性缺口，不必等事故」；§12 新增 #13（TM6 收口方案）。逻辑闭环。

## 我新揪出的（按该处理程度排序）

### NEW-1（最强，内部矛盾）— §4.2 与 §5.5 的 severity 映射公式对不上
§4.2 第 215 行白纸黑字：「映射表的输入必须显式包含『已升级次数』，`(reason, gate 阶段, 护栏等级, 升级次数) → severity`」。

但 §5.5 第 436 行写的是：「`(reason, gate 阶段, 护栏等级) → severity` 是一张固定表」——**少了「升级次数」**。

两节是同一张表的两种说法，现在一个含升级次数、一个不含。这正是这份 PRD 最自傲的「跨节一致性」，作者修 escalate 时只改了 §4.2 忘了同步 §5.5。

**修法**：§5.5 的映射公式补上 `升级次数`，或两处统一引用同一行定义。这是本轮唯一一个能叫「文档内部矛盾」的硬伤。

### NEW-2（具体，可能变 bug）— escalate 没有次数上限，存在重推循环风险
§4.2 说 `escalate` 会「提升 severity，换更强通道再推一次」，并引入升级次数进映射。但：
- §4.1 状态机没给 escalate 设上限；
- `on_expire` 的取值是按 reason 默认的（`agent_blocked` / `merge_conflict` 默认 `escalate`），而升级后的 Interrupt 其 `on_expire` 仍然可以是 `escalate`。

后果：一个无人理会的 `agent_blocked`，每次超时都 escalate 重推——若映射允许它一路升到 critical，就同时撞上 critical 熔断（§5.5 已兜底为汇总 HITL），但仍可能在触顶前反复重推、反复消耗通知通道。哪怕有熔断兜底，也该在状态机层写死「escalate 最多 N 次，之后转 `auto_reject` / `failed`」，而不是靠熔断去救。

**修法**：§4.2 给 escalate 加 `max_escalations` 或「升级次数达上限 → 终态」，与 NEW-1 一起改最干净（顺手把升级次数在映射里的作用写成「超过上限即封顶」，而非无限增）。

### NEW-3（战略级，最该一直盯着）— TM6 彻底解 与 「复用本机订阅 agent」直接冲突
§9.1 说 TM6 的彻底解是「Agent 跑在独立用户 / 容器 / 沙箱下」。但 §5.2（零凭证管理收益）、§3.2、§12 #1（已结案：走本机 agent CLI 如 `claude -p`）的核心价值正是**复用你已订阅的那份 coding agent、零额外 key**。

这两个前提正面冲突：沙箱里的独立用户**拿不到你本机已登录的订阅 agent 凭证**。要么接受「复用订阅」→ TM6 不闭合（V0 现状）；要么上沙箱闭合 TM6 → 放弃「复用本机订阅」的便宜，回到「Agent 也要自己鉴权」。

作者已经在 §12 #13 把它列为开放问题（「与其对复用本机订阅 agent 的影响」），**意识到了**。但我要强调的是：这不是普通 open question，是**整份 PRD 价值主张（零凭证 + 复用订阅）与威胁模型（TM6）之间唯一的、可能无法两全的架构分叉**。建议把它从「Backlog 立项时」提前到「DESIGN 必须正面回答」，因为答案会反过来改写 §5.2 的收益表（零凭证管理可能要加星号：仅在不上沙箱时成立）。

### NEW-4（微妙，TM6 缓解措施的漏网）— hooks 指纹应覆盖 `core.hooksPath` 重指向
§9.1 TM6 缓解写「git hooks 路径纳入启动期指纹；每次 Agent 结束后复核指纹」。但 Agent 的暴露路径里列了「写 hooks 或 `core.hooksPath`，在 Sift 自己执行 git 操作时取得执行」。

若 Agent 不改 hooks 目录内容、而是改 `.git/config` 把 `core.hooksPath` 指向别处，那么**对 hooks 目录本身的指纹校验抓不到**——指纹的是旧路径下的文件，新路径下的恶意 hooks 不在监控内。

**修法**：指纹对象应是「有效 hooks 解析结果」（含 `core.hooksPath` 的取值与最终指向目录的内容），而不只是默认 `.git/hooks` 目录。顺带 `.git/config` 本身也应入指纹。这是 TM6 缓解措施的一个真实缝隙，作者列得很全但漏了这一种 repoint 手法。

### NEW-5（两条小澄清，非阻塞）
- **§10.1「安全」验收的 scope**：该行列的是「验证 TM2/TM3（Agent 改 `.sift/**` 或 CI 配置被硬护栏拦下）」。但 TM6 明确说 `~/.sift/` 全局配置、git hooks、已登录 CLI 是**另一层、V0 不闭合**的暴露。读者容易把「PoC 安全通过」误读成「威胁模型闭合」。建议该验收行加个限定词（如「repo 级护栏 TM2/TM3」），与 TM6 的全局级开放明确分层。
- **TM6 缓解「运行期不热加载」的隐含代价**：allowlist / 配额等敏感配置启动期一次性读入，改了要重启 `siftd` 才生效。单用户 V0 完全可接受，但实现时容易当成 bug。建议在 §9.3 或开放问题里点一句「配置变更需重启生效」，免得实现阶段返工。
