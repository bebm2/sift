# WBS.md 评审（第 19 轮，D0.1 首评）

> 日期：2026-07-28
> 评审人：**cursor-opus5**
> 评审对象：[`docs/WBS.md`](../WBS.md) **D0.1**（796 行，对应 DESIGN D0.10 / PRD V0.8）
> 评审依据：[`docs/DESIGN.md`](../DESIGN.md) D0.10、[`docs/PRD.md`](../PRD.md) V0.8、ADR 002–013、[`design-review-18`](2026-07-28-design-review-kimi-k3-06.md) §7 划定的 WBS 复评重点
> 评审重点：（a）review-18 要求 WBS 验收必须携带的五组约束是否到位；（b）里程碑依赖是否可执行；（c）DESIGN / PRD 的模块与机制是否全部有落点

## 1. 结论

**不通过，建议先关闭 4 项 P1 再进入 `plans/` 与编码。**

WBS 的骨架是对的：八片与八里程碑 1:1、H1–H15 把 DESIGN 的结构性约束提到全局、V1–V15 有编号有归属、人工验收与自动化门禁分两组、`specs/` 按里程碑前置排布、风险表承接了 DESIGN §5.2 的三条逃生舱。review-18 点名的五组约束里有四组落到位（第 4 片五者同片、影子门禁无开关、控制面授权第 1 片、交叉编译第 1 片，见 H4–H7）。

但本轮发现 **4 项 P1**，其中两项是机械可验的排片错误，另两项是整块缺失：

1. **里程碑依赖成环**：M3 的验收标准里有两项分别依赖 M4 的 Gate 与 M5 的 Interrupt 发射器，而 M4 / M5 的前置又要求「M3 验收通过」；
2. **Brain（T1–T7）整个模块没有任务、没有 spec、没有里程碑**，而 M4 的 riskScore、M4 回放集的 Brain trace、M5 的 token 收费口与 PRD §3.1 PoC 第 2 步都以它存在为前提；
3. **状态机转移表与反向同步、V11 直接冲突**：缺 `waiting_human → done` 与 `queued → failed` 两条，而 2.4 与 V11 要求它们；
4. **`startup_stall` 人工态闭环没有实现任务**——ADR-013 的原子结果事务、`attempt_resolution` 的 CAS 仲裁、隔离标记与 worktree 不复用纪律全部缺失，WBS 只保留了「把 ADR-010 里的旧名改掉」这道文档前置检查。

第 4 项值得单独说一句：review-16 的三项 P1 正是靠 ADR-011 / ADR-013 的三套机制关闭的，review-18 也据此解除阻断。WBS 承接了 ADR-011（merge CAS，见 2.3、H13），却把 ADR-013 的两项只当成术语问题处理。**阻断解除的依据不能在下游文档里蒸发。**

## 2. 阻断项

### F1 · P1：里程碑依赖成环，M3 无法在 M4 / M5 之前验收

**位置**：WBS M3 验收标准（386–397）、M4 前置（403–406）、M5 前置（489–491）、V 汇总表 V5 行（750）、人工验收表 A5 行（773）。

M3 的验收标准里有两项当前不可执行：

| M3 验收项 | 依赖 | 依赖所在里程碑 |
|-----------|------|---------------|
| `.sift/**` 硬护栏拦截 \| V5 | Gate 的 `protected_paths` 判定 | **M4**（4.1） |
| 受控终止有界收敛为 Interrupt \| V4 | §8.7 单一发射器、生成去重键、注意力配额记账 | **M5**（5.1） |

而 M4 前置写「M3 验收通过」、M5 前置写「M4 验收通过」。两条依赖各自构成一个环，按字面执行无法开工。

同一错误在两张汇总表里复现：V 汇总表把 **V5 的对应测试切片与验收阶段都写成 M3**（750），人工验收表把 **A5「Agent 改动 `.sift/**` 或 CI 配置被硬护栏拦下」也挂在 M3**（773），而紧邻的 A6 挂 M4。DESIGN §12 的 V5 覆盖面是「`.sift/**`、CI 配置、base 策略与 context 读取源、head SHA fail closed」——只有「base 策略与 context 读取源」这一半属于 M3（3.4），护栏拦截那一半必须等 Gate。

M3 的 3.6 三结局第二条同样越片：「无法确认 → 经并发去重键生成一次 `startup_stall` Interrupt，Run 转 `waiting_human`」（373）。这不是可以缓一缓的呈现问题——DESIGN §10.1 明写「冻结不允许表现为 Run 静默停在 `queued`」，而 M3 若在没有发射器的情况下交付受控终止，交付出来的正好是那个被禁止的形态。

**必须修订**：

- V5 拆为两段：`V5a` 读取源（base vs worktree，M3 验收）与 `V5b` 护栏 fail closed（M4 验收）；A5 随 V5b 移到 M4，或明确 A5 由 V5b 承担而验收记录留在 M4；
- M3 的受控终止人工分支二选一：把 5.1 的发射器最小实现（单一入口 + 生成去重键 + 五件事同事务）提前到 M3，或把「收敛为 Interrupt」这条验收连同 3.6 第二结局一起移到 M5，M3 只验「确认消失」与「有界升级序列」两条；
- 前置链相应改写，不允许出现「A 的验收依赖 B，B 的前置是 A 的验收」。

推荐前者：发射器提前到 M3 的成本只是一个函数与一张表，而后者会让 M3 交付一个已知会静默挂死的系统，且 M4/M5 之间还要再补一次回归。

### F2 · P1：Brain（T1–T7）没有任务、没有 spec、没有里程碑

**位置**：全文。WBS 中 Brain 只作为被引用方出现三次——4.1「Gate 不调用 Brain」（421）、4.4「Brain 触点 trace」（457）、5.5「每日 token 上限（Brain 调用壳收费）」（541）。

没有任何里程碑分解出：T1–T7 七个触点、统一调用壳（调用 → decode gateway schema 校验 → 同 prompt 重试一次 → 走该触点的确定性兜底）、逐触点兜底表、提示词与 schema 同文件进 git 的版本化、agent CLI 的 usage 直接进预算表。`specs/` 清单也漏了 **`specs/brain.md`**（DESIGN §15 待写清单里有它）。

它不是可选项，四处硬依赖：

| 依赖方 | 需要 Brain 的什么 |
|--------|------------------|
| PRD §3.1 PoC 第 2 步 | 「Brain：一次 LLM 分派 → 选定 Agent + Goals」——PoC 闭环的必经节点 |
| WBS 4.1（421） | `gate(changeFacts, policy, riskScore)` 的 riskScore 由 T3 产出，且快照必须记录「T3 正常输出 vs 确定性兜底」的来源与版本（DESIGN §8.5） |
| WBS 4.4（457） | 回放集第二类可重跑对象是 Brain 触点 trace 含提示词与 schema 版本——PRD §5.6「量化提示词改动带来的漏放变化」的唯一依据 |
| WBS 5.5（541） | 三类预算的 token 收费口就在调用壳上；壳不存在则该预算没有收费点 |

顺带缺的还有 T7 校准提案（PRD §5.9 允许的两类产物）与 T5 失败分诊（4.1 的判定顺序第 2 步引用了它，416）。

DESIGN §13 的切片表同样没点名 Brain，所以这不是 WBS 单方面的疏漏；但**WBS 是「谁在哪一片交付它」必须有答案的地方**，不能两份文档互相假设对方安排了。

**必须修订**：把 Brain 拆进里程碑并补 spec。建议排布：

- **M1**：调用壳骨架 + 逐触点兜底的接线（可先只接 T2，走 fake Brain），使 1.8 的骨架闭环有分派节点；
- **M2**：T1 体检（Intake 侧）；
- **M4**：T3 风险评分 + T5 失败分诊（Gate 的输入与判定顺序需要它们），并在 4.4 落 Brain trace 的写入点；
- **M5**：T4 决策简报 + T6 打扰调度（Interrupt 的 `headline`/`brief`/`options` 与推送时机）；
- **M7 或延后**：T7 校准提案（PRD §5.3 已写明兜底为「不做」，可不进 V0 门禁但要有明确处置）；
- `specs/brain.md` 前置于 M1，随触点落地增补。

### F3 · P1：状态机转移表缺两条，与 2.4 反向同步、V11 直接冲突

**位置**：WBS 1.3 合法转移表（107–116）、2.4 反向同步（254–258）、V 汇总表 V11 行（757）。

1.3 逐字复制了 PRD §4.1 的九条转移。但 2.4 要求实现四条反向同步，其中两条落不到这张表上：

| 2.4 的要求 | Run 当时最可能的状态 | 需要的转移 | 1.3 是否有 |
|-----------|-------------------|-----------|-----------|
| Change 手动合并 → `done` + `gate_bypassed`（256） | `waiting_human`（正卡在 `code_review`） | `waiting_human → done` | **无** |
| Issue 关闭 → `failed`（`closed_upstream`，255） | `queued`（尚未分派或等并发槽） | `queued → failed` | **无** |
| 触发标签移除 → `failed`（`untriggered`，258） | `queued` | `queued → failed` | **无** |

第一条尤其硬：**V11 是 M2 的验收项**（757：「门禁未过时合并 → `done` + `gate_bypassed`」），而「门禁未过」最典型的现场就是 Run 正停在 `waiting_human` 等人审。按 1.3 的表实现，`transition()` 会对这条合法的外部事实抛错——而 1.3 自己要求「非法转移抛错而非静默忽略」（118）。于是 M2 的 V11 必然失败，且失败原因是 M1 的转移表。

这两条的缺失源头在 PRD §4.1 的状态图（它把 `↘ done` / `↘ failed` 都挂在 `running` 上），不是 WBS 编错。但 WBS 是两侧要求首次在同一份文档里相遇的地方，因此必须在这里收口。

**必须修订**：

- 回 PRD 补 §4.1 的两条转移（`waiting_human → done`、`queued → failed`），或明确「反向同步统一先经 `→ running` 中转」这一等价实现并写进 1.3；
- 前者更干净：`done` 已经被 PRD V0.3 裁定为纯外部事实，`waiting_human → done` 与该裁定同源；`queued → failed` 对应 PRD §4.5 的两条既有要求，不引入新语义；
- V1 属性测试的「所有非法转移被拒」需要一张确定的全集表，因此这条不能留到实现时补。

### F4 · P1：`startup_stall` 人工态闭环没有实现任务，ADR-013 被降级为改名

**位置**：WBS 文档前置检查（17–25）、1.2 `attempts` 列（94）、3.6（365–374）、5.1–5.3（495–532）、M6 故障注入（601）、V2 行（747）。

WBS 里与 `attempt_resolution` 相关的内容只有三处：文档前置检查要求给 ADR-010 加改名指针（21–23）、1.2 的 `attempts` 表多一列（94）、M6 故障注入里一行断言「retry 两段式（探测失败复用同一 Interrupt、计数+1、nonce 轮换；探测成功原子回 `queued`）」（601）。

**没有任何任务实现它背后的四套机制**，而这四套是 review-16 三项 P1 的关闭依据（DESIGN §14.13 F2/F3、ADR-013）：

| 缺失机制 | DESIGN 出处 | 为什么不能留给实现者 |
|---------|-----------|-------------------|
| `attempt_resolution` 的 CAS 仲裁与迟到事实优先表 | §10.1「迟到的启动事实与 attempt 的落定结果，谁先落库谁生效」 | 三种可能实现各自违反一条承诺（R14-F1 原文），选错即活着的 Agent 无人监督 |
| retry 探测成功的**单笔 CAS 事务** | §10.1 + ADR-013 | 分事务执行会产生「Interrupt 已关但没有新 attempt」「Run 已 `queued` 但启动未入 outbox」两种静默挂起 |
| **隔离标记**：worktree 既不回收也不被任何新 attempt 复用 | §7、§10.1「『放弃』不等于『执行体已消失』」 | DESIGN 原文点名这是「这一整节最容易犯的错」，犯了就是在可能仍被写的 worktree 上开第二个 agent |
| 四个入口共享同一套 CAS 前置与幂等结果 | §10.1 末段 | `claim:started`、恢复补 started、迟到 `result.json` 吸收、Interrupt 指令必须是同一函数的四个调用点 |

其中隔离标记连**数据模型都没进**：1.2 的 `attempts` 列写了 `attempt_resolution` 但漏了隔离标记（94），而 DESIGN §7 的 attempt 行明写「人工态下另有不可逆的 `attempt_resolution` marker 与**隔离标记**（隔离期间 worktree 不回收、不被任何新 attempt 复用）」。M8 的 `sift doctor` 要「持续报告它」（DESIGN §10.1），8.5 也没这一项（713–720）。

人工分支的动作集同样缺失：DESIGN §10.1 规定这条 Interrupt 的 `options[]` 收窄为 `retry` / `reject` / `hold` 且 **`approve` 必须不在 options 内**，5.1 与 5.3 都没有按 reason 收窄动作集的任务（5.3 只有通用的「指令属于当前 Interrupt 的 `options[]` 校验」，529）。V10a 的对应断言「对 `startup_stall` 发 `approve` 必须被拒」（DESIGN §12）在 WBS 的 V10a 行（755）被压缩成「指令 options[] 校验」，丢了这个点名用例。

**必须修订**：

- 在 M3 或 M5 明确落一节「人工态仲裁与 retry 两段式」，逐条列出上表四套机制 + 动作集收窄，并注明派生自 ADR-013；
- 1.2 的 `attempts` 补隔离标记列，`interrupts` 补 `superseded_by_fact` / `superseded_by_decision` 的关闭原因；
- M5 验收表增两行：「迟到 `started` 事实优先 / 决定吸收各自收敛 | V4」「retry 探测成功为单笔原子事务 | V2」；
- 8.5 `sift doctor` 增「隔离中的 attempt 与未回收 worktree 报告」；
- 该节归属需与 F1 一并决定：它同时依赖 attempt 恢复（M3）与 Interrupt / Command（M5）。

## 3. 重要非阻断项

### F5 · P2：3.5 的恢复矩阵只列了 12 行，DESIGN 有 18 行，且缺的正是 §14.10 自查修掉的那一行

**位置**：WBS 3.5（347–363）对 DESIGN §10.1 矩阵（764–785）。

WBS 写「实现全部 attempt 阶段的恢复动作（DESIGN §10.1 矩阵）」后逐条列了 12 项。既然列了，它就会被当成全集读。实际漏 6 行：

| 漏掉的观测行 | 后果 |
|-------------|------|
| `spawning`（Agent 已落盘、进程与 result 都不在） | wrapper 仍在时应限时等其落 result，漏了会直接判 `orphaned` |
| `running`（`result.json` 存在且**失败**） | WBS 把成功/失败合并成一行「按结果推进」，退避重试与 `failed` 的分叉丢失 |
| `running`（进程存在但 heartbeat 过期） | 缺 fail closed 路径 |
| **`running`（后端会话在、wrapper 不在）** | **必须先走受控终止确认进程组消失再判 `orphaned`** |
| `running`（wrapper 在、后端会话不在） | 缺「以 wrapper 为准继续监督并告警」 |
| 任意（多 wrapper 竞争 / 旧 generation 苏醒） | 缺 CAS 拒绝与安全事件记录 |

第四行是重点：DESIGN §14.10 的作者自查专门把它从 P2 修掉了，理由是「不确认就判 `orphaned` 加一次人工 `retry`，等于在同一 worktree 上放第二个 agent」，并据此把纪律从 `spawning` 推广到「凡在执行者可能仍存活时判 `orphaned` 都必须先走受控终止流程」。WBS 3.6 把受控终止写成「单一实现，三路径复用」（367）是对的，但 3.5 的枚举没有体现这条推广后的适用面，而 M3 验收又只写「恢复矩阵逐行断言 | V4」——「逐行」指的是哪张表，就此变成实现者的解释空间。

**建议**：3.5 改为不逐条复制、只写「逐行实现 DESIGN §10.1 全表（18 行）」+ 链接，并把「凡执行者可能存活时判 `orphaned` 必先走受控终止」单列为一条验收；若坚持列举则必须补全 6 行。前者更符合 WBS 自己声明的「引用不复制」。

### F6 · P2：ADR-012 的资格制度只排到 M7，M3 / M6 的自动 retry 未以资格为条件

**位置**：WBS H14（46）、3.5–3.6、M6 故障注入（594–602）、7.4（648–653）。

WBS 对 ADR-012 的承接是：H14 声明「`process-group-verified` 是 Agent 资格结论，不得写成 TM6 或沙箱已闭合」，7.4 在 M7 做拓扑资格测试并进 `doctor`。这两条都对，但**漏了资格制度的执行侧**。

DESIGN §10.1 判定纪律第三条写明：「『进程组消失 ⇒ 执行体消失』只对 `process-group-verified` Agent 成立；未验证组合不能据此自动新开 attempt，必须保持隔离并转人工」。这是一条**恢复与受控终止代码里的分支**，落在 M3；DESIGN §12 的 V4 也把它写成 M3/M6 的断言：「**进程拓扑资格**覆盖每个真实 agent CLI / 版本，构造脱组后代时必须标 `process-group-unverified` 且禁止自动 retry」。

WBS 的 3.5 / 3.6 没有任何一处以资格状态为条件，M6 的故障注入全矩阵（594–602）列了七组，没有「构造脱组后代」这一组。于是 M3 会先实现一个把进程组消失当作绝对证据的版本，M7 再补一张报告——报告与代码分离，正是 H14 想防的「把资格结论写成已闭合」的另一种形态。

**建议**：3.5 或 3.6 增一条「消失证据的采信以 attempt 所用 agent 的资格状态为条件，`unverified` 一律走『确认不了』分支」；M6 故障注入增「构造脱组后代 → 必须标 `unverified` 且禁止自动 retry」；M3 验收增对应行。资格**数据**的采集可以留在 M7，资格**门控**必须与恢复同片。

### F7 · P2：ADR-011 的「能力探测失败即不得自动合并」有任务无验收

**位置**：WBS 2.3（244）、M2 验收标准（281–290）、H13（45）。

2.3 最后一条写了「适配器无法提供条件语义时，能力探测失败，Sift 不得自动合并」，这条是 ADR-011 的核心防线（DESIGN §6.4：「不得退化为无条件 merge」）。但 M2 验收表只有「merge CAS 拒绝 stale head | V3」，没有一项验「探测失败 → 自动合并被禁用」；H13 也只写了「merge 请求必须携带 expected_head_sha」，没写探测失败时的行为。

review-18 §7 明确把「ADR-011 的能力探测失败即禁用自动合并」列为 WBS 验收必须携带的项之一。有任务无验收的条目在实现期最容易被简化成「探测失败就记个 warning」。

**建议**：M2 验收增一行「适配器不支持条件合并时 `auto_merge` 被结构性禁用（不是告警）| V3 + 代码检视」；H13 补后半句。

### F8 · P2：V12 有归属无任务无验收，V9 在 M1 被降级为手动

**位置**：WBS V 汇总表 V12 行（758）、V9 行（754）、M1 任务分解（74–174）、M1 验收标准（182–193）。

两处汇总与正文不一致：

- **V12 零配置启动**：汇总表写「M1 / M1 验收」，但 M1 的九个任务组里没有它，M1 验收表八行里也没有它。DESIGN §12 与 §14.2 反复强调 V12 的存在理由——「都有确定性默认值」这句承诺在文档里无法验证，只有零配置启动测试能让漏掉的默认值在 CI 里失败而不是在用户机器上表现为拒绝启动。它同时是 §14.2 点名的五个启动协议时限的唯一保障。
- **V9 端到端**：汇总表写「M1、M7 / M1 + M7」并归入自动化门禁，但 M1 验收表把它写成「fake Forge/Agent 骨架闭环跑通 | **开发者本地手动验证**」。DESIGN §12 的分组表把 V9 的 fake 链放在自动化门禁一侧，人工验收只含真实链那一半。M1 若不把 fake 全链做成 CI 断言，后续每片的回归都失去最便宜的护网。

**建议**：M1 增 1.10「零配置启动测试 + 默认值表对账」并进 M1 验收；M1 验收的 V9 行改为「fake Forge/Agent 全链在 CI 内跑通 | V9」，手动验证只作为补充。

### F9 · P2：启动期探测的两级分层没有任务

**位置**：DESIGN §11（868–875）、§9.4；WBS M1 1.6（143–156）、M2 2.1（228）。

DESIGN §11 用一张两级表关闭了 review-05 的 F4（R5-F4）：**进程级**失败（SQLite 与迁移、全局配置 schema 与指纹、agent CLI、被引用到的 forge CLI 登录与版本）拒启 daemon；**项目级**失败（单项目 `.sift/policy.yaml` schema 校验、运行期 `AuthOrCapability` 失效）只隔离该项目，其余项目照常调度。原始问题是「一个坏仓库会停掉全部健康项目」。

WBS 只有两条零散承接：1.6 的 `doctor` 骨架检查项里列了「项目策略 schema」（153），2.1 末条写「Forge 能力探测只探测已配置项目引用到的；失败即拒启」（228）。**没有任何任务实现分级本身**，也没有验收断言「单项目 policy 非法时其余项目照常调度」。按现状实现，最可能的结果就是回到被 R5-F4 否掉的那一版。

**建议**：M1 增一条「启动期探测分进程级 / 项目级两级，逐级行为按 DESIGN §11 表」，M2 补运行期 `AuthOrCapability` 的项目级隔离；M1 或 M2 验收增「坏仓库不影响健康项目调度」一行。

### F10 · P2：指标打点没有任务，而 V11 的验收口径依赖它

**位置**：PRD §10.2、DESIGN §9.3；WBS 全文、V11 行（757）。

PRD §10.2 的标题就是「指标（V0 就打点，不等 PoC 之后）」，DESIGN §9.3 承接为「八项指标全部从事件流与账本派生，V0 就打点」，并定下北极星的代理口径（加权打扰次数 / 已合并 Change，权重表是配置项）。WBS 没有任何一处安排它。

这不只是漏一个观测功能：**V11 的断言含「不计入误放行率分母」**（757），而误放行率的分母口径（只含 Sift 发起的合并）与门禁绕过率是 PRD §10.2 与 §4.1 一起裁定的产物。没有指标实现，V11 只能验前半句。同理 M5 的注意力配额消耗率、`sift ps` 的今日余量（DESIGN §8.10）也没有落点。

PRD §5.9 的采集论证在这里同样适用——「写字段很便宜，补历史不可能」。

**建议**：M4 或 M5 增一节「指标派生与打点」（八项指标的事件来源、权重表配置项、`gate_bypassed` 与误放行率分母口径），并把「不计入误放行率分母」这半句的验收挂到该节所在里程碑。

### F11 · P2：M1 的骨架闭环写入了 Gate 与合并，与 H5 冲突

**位置**：WBS 1.8（163–167）、H5（37）、里程碑总览 M1 行（55）。

1.8 写「端到端骨架闭环（Issue 摄入 → 分派 → 执行 → Gate → 合并）」。但 H5 自己规定 Gate 与影子门禁、认证投影、回放集、Change 创建五者同在**第 4 片**，M4 才交付。M1 期不存在 Gate。

这一条按字面执行有两种坏结果：要么实现者做一个临时 Gate（等于在 M4 之前引入第二条裁定路径，直接违反 DESIGN 原则 1「想禁止的事，做法是让实现它的函数不存在」），要么把 M1 的闭环验收模糊处理。DESIGN §13 第 1 片写的是「fake Forge/Agent 跑通闭环」，没有把 Gate 列进去。

**建议**：1.8 改写为「Issue 摄入 → 分派 → 执行 → attempt 完成证据 → 直接合并（M1 期无 Gate，不得引入临时裁定）」，并在 M1 验收注明「Gate 缺位是刻意的，M4 接入时该路径必须被替换而非并存」。

## 4. 次要项

### N1 · P3：`startup_stall` 的 `on_expire` 限制没有写进 5.2

5.2 写了通用的「`expires_at` + `on_expire`：`hold` / `escalate` / `auto_reject`」（514）与「达上限封顶 severity + 落 `hold`」（515），但没写 PRD §4.2 的硬规则：**`startup_stall` 禁用 `auto_reject`，且达升级上限后落 `hold` 而非终态**。这条是 review-16 F2 的关闭内容（DESIGN §14.13），按 reason 生效，不能靠通用配置表达。建议 5.2 单列一行，并在 M5 验收增「`startup_stall` 不可配置为 `auto_reject`」。

### N2 · P3：「探测在途时该 Interrupt 不接受新指令」缺失

DESIGN §10.1 的两条配套约束里，5.2 落了「每次升级重新签发 nonce」（518），漏了「探测在途时该 Interrupt 不接受新指令，服务端回『已在探测中』」。缺了它，人连点两次 `retry` 会变成并发探测。建议补进 5.3 的四步之后。

### N3 · P3：`sift doctor` 的检查项在 M1 与 M8 之间有漏项

1.6 的 `doctor` 骨架（153）与 8.5 的最终检查（713–720）合起来，仍缺 DESIGN §8.10 要求的两项：**hooks 指纹**（M3 3.7 实现了指纹，但没有任务把它接进 `doctor`）与**项目策略漂移横向对比**（PRD §5.7 的明文要求，WBS 只在 `specs/policy.md` 的括号里出现「漂移判定口径」，471）。建议在 3.7 与 M4 各补一条接线任务。

### N4 · P3：forge API 预算在 2.4 与 5.5 重复出现，所有权不明

2.4 写「API 预算：配置每小时调用上限，接近上限自动降级为慢轮询并告警」（253），5.5 又写「每小时 forge API 上限（Forge 适配层收费）」与超限降级（542、546）。DESIGN §9.2 定的收费口是 Forge 适配层（M2），而 V8 的断言在 M5。两处并存会让「谁负责实现」变成解释题，也违反 WBS 自己引用的「引用不复制」。建议 2.4 保留实现、5.5 改为只写「验证三类预算并存与各自降级」并链接。

### N5 · P3：A8 无对应任务

人工验收表 A8「配置中存在 ≥2 个 Agent 定义且均通过校验；1 个真实跑通」挂在 M7（776），但 7.1–7.5 只有「至少一种真实 Agent 端到端跑通」（626），没有「第二个 Agent 定义通过校验」的任务，也没有 Agent 定义 schema 校验的落点（PRD §3.2 把它作为「两种 Agent 各跑通一次」的降级替代，是 PoC 成功标准之一）。建议 7.1 补一条，并把 Agent 定义 schema 归到 `specs/config.md`。

### N6 · P3：Ledger 的语义原料留存无任务

1.2 的 `calibration` 表列了「语义原料」（99），4.3 与 `specs/ledger.md` 也提到它，但没有任务负责在 `/sift reject <原因>` 与 `/sift ask <文本>` 执行时把自然语言写进账本。PRD §5.9 称它是「全系统信息密度最高的数据，目前被直接丢弃」，且明确这是无法回溯补录的采集决策。建议 5.3 Command 的四步之后补一条写入任务。
