# DESIGN.md 架构评审（第 2 轮）

> 日期：2026-07-27  
> 评审对象：[`docs/DESIGN.md`](../DESIGN.md) D0.1（对应 PRD V0.2）  
> 评审依据：[`docs/PRD.md`](../PRD.md)、[`docs/README.md`](../README.md) 及 DESIGN 引用的 active ADR  
> 评审范围：权限边界、一致性与幂等、恢复模型、调度公平性、Gate 安全门槛、状态语义

## 1. 结论

**当前版本不建议直接进入 WBS 拆解或实现。**

整体架构方向清晰：单写者、唯一状态转移入口、纯函数 Gate、transactional outbox、wrapper 恢复契约，以及对 TM6 未闭合边界的诚实声明，均是合理的结构性选择。

但文档仍有 4 个阻断级问题和 2 个重要问题。其中三个问题会使文档声称的结构性保证实际不成立：Agent 可绕过 Report 权限边界访问运维控制面；outbox 尚不足以提供通用的“恰好一次”；`auto_merge` 证据门槛没有合法、可审计的数据流。另一个阻断项是 Agent 启动过程的崩溃窗口未被恢复矩阵覆盖。

建议修正这些问题后再进入 WBS，并同步检查 ADR-003、ADR-005、ADR-006 是否需要追加替代 ADR 或补充说明。

## 2. 问题汇总

| 编号 | 级别 | 问题 | 主要影响 |
|------|------|------|----------|
| F1 | P1 | Agent 可绕过 Report 权限边界访问运维控制面 | Layer 1 “永不越权”不成立 |
| F2 | P1 | Outbox 机制不足以保证通用的“恰好一次” | 重复评论、通知或 Agent 启动 |
| F3 | P1 | `auto_merge` 证据门槛缺少合法数据流与版本快照 | 自动合并安全门槛不可实现或不可审计 |
| F4 | P1 | 恢复矩阵遗漏 Agent 启动阶段的崩溃窗口 | 幽灵 running、重复启动或漏管进程 |
| F5 | P2 | 固定优先级可能让 outbox 永久饥饿 | 已提交副作用无限延期 |
| F6 | P2 | 手工合并事实与 `done`/Gate 不变量冲突 | 状态机无法一致表达外部事实 |

## 3. 详细发现

### F1 · P1：Agent 可绕过 Report 权限边界访问运维控制面

**位置**：DESIGN §8.9–§8.10，约第 399–411 行；相关拓扑见 §3.2。

DESIGN 通过 `SIFT_RUN_ID` 和 attempt 作用域的 `SIFT_RUN_TOKEN` 限制 `sift report`，并据此声称 Layer 1 不存在写 `runs.status` 的操作。然而 Agent 与用户 CLI 运行在同一 UID 下，共享属主可访问的 Unix socket。Agent 本身具备执行 shell 命令的能力，因此不仅可以调用 `sift report`，也可以调用 `sift kill`、`sift retry` 等运维子命令，或直接构造 socket 请求。

`0600` 只能隔离其他系统用户，不能隔离同属主 Agent。Run token 只约束 Report RPC，也不能阻止 Agent 使用未携带该 token 的运维 RPC。因此“Report 工具集没有改状态函数”并不是完整的能力边界。

**影响**：

- Prompt injection 可从 Agent shell 直接进入本地控制面；
- Agent 可能终止或重试其他 Run；
- §2.3 与 §8.9 所称“结构性保证”不成立；
- TM6 暴露面清单遗漏了 `siftd.sock` 与运维 CLI。

**建议**：

1. 为 socket 上的每一类 RPC 明确定义服务端授权模型，不能只描述 Report token；
2. 将运维 RPC 与 Run RPC 分成不同能力或不同端点，并说明 Agent 为什么无法取得运维能力；
3. 若同用户 V0 无法真正隔离，应把控制 socket 加入 TM6 未闭合清单，并把“Layer 1 永不越权”改为条件性声明；
4. 在安全测试中加入“Agent 调用 `sift kill/retry` 或直接访问 socket 必须失败”的用例；若 V0 预期不能失败，则诊断输出必须明确报告该暴露面。

### F2 · P1：Outbox 机制不足以保证通用的“恰好一次”

**位置**：DESIGN §2.2 Q5、§6.4、§10.2，约第 56、234–238、521 行；ADR-003 同样作出该保证。

Transactional outbox 能保证本地事务提交后副作用不会被静默遗忘，但它本身只提供**至少一次尝试**。稳定的本地 operation key 加“先查询远端证据再动作”仍有两个窗口：

1. 查询确认未执行后，另一个执行者或重试同时执行；
2. 远端动作已经成功，但本地尚未记录成功时进程崩溃。

只有远端 API 接受幂等键，或存在可被无歧义查询且与动作原子绑定的远端标记，才能把具体动作收敛为 effectively-once。当前文档没有逐类给出此契约，尤其没有说明 Agent 启动和未选定 Channel 的幂等证据。

**影响**：

- Q5“最终恰好生效一次”目前不可由通用 outbox 推导；
- 可能重复启动 Agent、重复发送通知或评论；
- V2/V7 即使通过本地崩溃测试，也不足以证明跨系统恰好一次。

**建议**：

1. 在 `specs/` 中为每种副作用定义独立的幂等协议：operation key 如何传播、远端证据是什么、证据冲突如何处理；
2. 对无法提供可靠幂等证据的 Channel 明确采用至少一次投递，并让消息携带可见去重标识；
3. 为 Agent 启动设计 attempt 级互斥协议，例如由 wrapper 在启动真实 Agent 前原子取得 attempt claim，重复 wrapper 自动退出；
4. 将 Q5 收窄为可验证的表述，例如“已定义幂等协议的副作用 effectively-once；其余至少一次且重复可识别”。

### F3 · P1：`auto_merge` 证据门槛缺少合法数据流与版本快照

**位置**：DESIGN §8.5–§8.6，约第 354–365 行；缓存键见 §6.5。

§8.5 要求策略加载器根据影子门禁证据剔除未达门槛的 `auto_merge`，但 §8.6 又规定 Ledger 的读取面只有 T7 和指标计算两个消费者。架构图和模块说明中不存在负责计算“某类任务是否已认证”的消费者或投影。

此外，认证证据会随着运行持续增长。“策略加载期的一次校验”如果只在启动或首次加载时执行，资格状态会陈旧；如果每次 Gate 前重新计算，则必须冻结当时的认证快照，并使 Gate 缓存随认证状态变化而失效。当前缓存键只有 `run_id + head_sha + gate_version + policy_blob_hash`，没有认证版本或证据快照。

**影响**：

- `auto_merge` 可能永远无法自动启用，或使用已经过期的认证结果；
- 回放时无法解释当时为何允许或禁止自动合并；
- Ledger 的消费者约束与有效策略计算互相矛盾；
- 安全门槛变化后，旧 Gate 缓存可能继续生效。

**建议**：

1. 增加确定性的 certification projection，明确它是 Ledger/校准数据的合法聚合消费者；
2. projection 只产出按任务类别聚合的门槛认证，不允许影响单条判断，以继续满足 A7；
3. 将认证版本、统计窗口和阈值版本冻结进有效策略与 Gate 输入证据；
4. 将 certification version 或有效策略 hash 纳入缓存键；
5. 明确认证数据变化后的失效与重新判定规则。

### F4 · P1：恢复矩阵遗漏 Agent 启动阶段的崩溃窗口

**位置**：DESIGN §6.4、§10.1，约第 234、505–517 行；ADR-005 只覆盖 wrapper 已落盘后的恢复。

启动 Agent 是 outbox 副作用，但文档没有定义 `queued → running` 与“wrapper 实际启动”的提交顺序。两种顺序都有必须处理的窗口：

- 先将 Run 置为 `running`，再启动 wrapper：可能留下 `running`，但没有进程、会话或 `result.json`；
- 先启动 wrapper，再将 Run 置为 `running`：可能留下仍为 `queued`、但已有活进程的 attempt。

当前恢复流程只核对 `running attempt`，矩阵也没有“结果、wrapper 和后端会话均不存在”这一分支。第二种窗口甚至不会进入扫描范围。

**影响**：

- 违反 Q1 和 PRD 的“无幽灵 running”；
- 可能漏管仍在执行的 Agent；
- outbox 重试可能再次启动同一 attempt；
- 无法判断应该重试、失败还是继续等待启动操作。

**建议**：

1. 将 Run 状态与 execution attempt 生命周期分开建模；attempt 至少需要表达 pending/starting/running/finished 或等价阶段；
2. 启动 outbox operation 与 attempt claim 建立唯一约束；
3. 启动期恢复扫描所有非终态 attempt 和未完成的 start operation，而不只扫描 `running`；
4. 补齐“无结果、无进程、无会话”“queued 但进程存在”“多个 wrapper 竞争同一 attempt”等恢复行；
5. 把这些崩溃点加入 V2/V4 故障注入矩阵。

### F5 · P2：固定优先级可能让 outbox 永久饥饿

**位置**：DESIGN §6.1，约第 193–201 行。

文档规定每个 tick 执行一步转移，并按固定顺序处理 intake、反向同步、Checks、HITL、重试，最后才推进 outbox。如果实现为严格优先级，只要高优先级队列持续有工作，outbox 就可能永远没有执行机会。

**影响**：

- 已提交的通知、评论、Change 创建、合并和 Agent 启动无限延期；
- Q5 的“最终生效”无法保证；
- `waiting_human` 可能已经成立，但对应 Interrupt 长时间未发布。

**建议**：

采用可证明公平的调度规则，例如加权轮转、每类每 tick 的有界配额、最大连续高优先级次数，或同进程内独立且可唤醒的 outbox 推进器。无论采用哪种方式，都应定义 outbox 最大推进延迟并加入负载测试。

### F6 · P2：手工合并事实与 `done`/Gate 不变量冲突

**位置**：DESIGN §8.2，约第 305 行；对应 PRD §4.1、§4.5、§10.1。

DESIGN 按 PRD §4.5 将 Change 手工合并视为事实并直接收敛，但 `done` 的定义是“Change 已合并且门禁通过”，PoC 标准又要求硬护栏违规任务不能进入 `done`。

若用户在 Gate 尚未通过、或已经发现硬护栏违规时手工合并 Change，当前五状态模型无法同时表达以下三个事实：Change 已经合并、Gate 未通过、本地不得进入 `done`。

**影响**：

- reconciler 对同一观测可能得出互相冲突的转移；
- 外部事实源原则与本地安全不变量无法同时满足；
- 指标可能把门禁违规的手工合并计为正常完成。

**建议**：

该冲突源自 PRD 已拍板语义，DESIGN 不应自行选择。应回到 PRD 明确以下两种口径之一：

- `done` 只表示外部 Change 已合并，Gate 结果作为独立审计属性，成功标准限定为“Sift 发起的合并不得绕过硬护栏”；或
- 增加能够表达“已外部合并但门禁失败”的终态/结果维度。

随后在 DESIGN 中写明事实与 Gate 冲突时的优先级和指标口径。

## 4. 建议修订顺序

1. 先解决 F6 的 PRD 语义冲突，避免 DESIGN 在错误状态模型上继续展开；
2. 明确 F1 的控制面授权边界，并同步 TM6 声明；
3. 联合修订 F2 与 F4，完整定义副作用语义、attempt 生命周期和恢复协议；
4. 修订 F3，补齐认证投影、快照与缓存失效；
5. 最后补充 F5 的公平调度规则和验证场景；
6. 同步更新受影响的 ADR、追溯表和验证策略。

## 5. 复评通过条件

- Agent 无法通过 Report 之外的本地 RPC 改变任何 Run；若 V0 无法保证，文档明确列为未闭合边界；
- 每类副作用都有可验证的投递与去重语义，不再由通用 outbox 推导“恰好一次”；
- `auto_merge` 认证数据流、快照、缓存失效和回放证据闭合；
- 启动前后每个崩溃窗口在恢复矩阵中都有唯一、确定的收敛动作；
- outbox 在持续负载下具有有界推进延迟；
- 手工合并与 Gate 冲突时有唯一状态语义和指标口径。
