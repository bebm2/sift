值得肯定的是：D0.2 对前三轮发现的处置质量很高——不是补丁式修补，而是把每条发现升级为**结构性保证或显式声明**。§14.5 的处置对账表逐条可追溯，其中 F1（端点分离 + 声明收窄）、F3（认证投影）、F4（attempt 生命周期）三条的处理方式尤其到位：不是简单加一行文字，而是补了完整的机制（两个 socket、第三个账本消费者、独立生命周期建模 + 恢复矩阵补行）。

## 3. 本轮新发现

### M1 · P2：Gate 缓存键缺失 riskScore 维度

**位置**：§8.5（函数签名与缓存说明）、§6.5（缓存键）、ADR-004 第 23 行。

Gate 函数签名是 `gate(changeFacts, policy, riskScore) → verdict`，三个显式输入。缓存键为 `(run_id, head_sha, gate_version, effective_policy_hash, certification_version)`，其中：

| 输入 | 缓存键捕获维度 |
|------|---------------|
| `changeFacts` | `head_sha`（确定性，同一 commit → 同一 diff） |
| `policy`（有效策略） | `effective_policy_hash` |
| `certification_version` | 独立维度 |
| **`riskScore`** | **无** |

`riskScore` 是 T3（Brain 触点）的输出——**非确定性 LLM 调用**。当 T3 失败时走确定性兜底（PRD §5.3：视为高风险 → 强制人审）。此时 Gate 以兜底 riskScore 运行，verdict 被缓存。后续 tick 中同一 `head_sha` 命中缓存，T3 不再重跑，即使 Brain 已恢复，该 Run 仍被锁定在基于兜底风险分的裁定上。

**影响**：非安全缺陷（兜底偏向保守，不会导致漏放），但在 `review_policy: risky-only` + 已认证 `auto_merge` 的场景下，T3 的一次失败会令一个本可自动合并的 Run 永久进入 HITL。更重要的是：缓存键被显式枚举为设计决策（DESIGN §6.5 + ADR-004），它声称捕获了全部失效维度，实际遗漏了一个显式输入。

**建议**：二选一——

1. 将 riskScore（或完整输入快照的 hash）纳入缓存键，使 T3 输出变化时旧缓存自动失效；或
2. 显式声明「T3 兜底裁定一经缓存即被接受，不因后续 T3 恢复而重新评估」作为有意识的设计取舍，并说明理由（保守偏向 + 同一 head_sha 下 T3 正常只调一次）。

当前两种表述都不存在，缓存键的完备性是隐含主张但未兑现。

### M2 · P3：§3.3 架构拓扑图与 §3.2 / §6.1 文字描述不一致

**位置**：§3.3 mermaid 图（第 111–129 行）。

图中两处简化与正文的核心结构性主张不一致：

1. **`Sock[[Unix socket 控制面]]` 是单节点**，但 §3.2 花整节论证「两个 socket，两类能力」是端点分离的结构性保证。图把 `siftd.sock` 与 `run.sock` 合并成一个节点，且 `Ag -->|sift report| Sock` 让 agent 报告与运维 RPC 看似走同一通道。
2. **`Tick[Tick 调度器]` 是单节点**，但 §6.1 定义了三组独立步频调度器（Intake / Supervisor / Outbox），并论证单一主循环会饿死 outbox（F5 的修复）。

**影响**：图的读者（含 AI 编码代理）会得到与正文矛盾的拓扑印象。端点分离是 §3.2 的核心论点（「不是为了整洁，是为了让边界可被沙箱一次关掉」），图不支持这个论点。

**建议**：图中将 `Sock` 拆为 `OpsSock[siftd.sock · 运维]` 与 `RunSock[run.sock · 报告]` 两个节点，agent 连 `RunSock`、CLI 连 `OpsSock`；将 `Tick` 拆为三个调度器节点或至少标注「三组步频」。文字是权威、图是辅助，但二者不应打架。

### M3 · P2：§8.4 attempt 生命周期图遗漏 `starting → orphaned` 转移

**位置**：§8.4 attempt 生命周期图（第 400–403 行）与 §10.1 恢复矩阵（第 625–637 行）。

§8.4 的生命周期图展示：

```
pending → starting → running → finished
                     ↘(claim 未落) → pending     running → orphaned
```

`orphaned` 只从 `running` 分出。但 §10.1 恢复矩阵有一行：

> `starting` | claim 已落、进程不存在、无 `result.json` | 判 `orphaned`；释放 claim，按重试策略新开 attempt 或转 `failed`

即 **`starting → orphaned`** 存在但图中缺失。这个窗口是真实的：wrapper 取得 claim 后、写完 `control.json` 前（或写完后、达到 `running` 状态前）崩溃，attempt 处于 `starting` 且 claim 已占但进程已死。恢复矩阵覆盖了它，但用于推理崩溃窗口的生命周期图没有表达它。

**影响**：生命周期图是实现者推理崩溃窗口的首选参照（§10.1 矩阵是其细化）。图中缺一条转移，实现者可能在恢复逻辑中遗漏对应的收敛路径。ADR-005 第 36 行也只提到「claim 已落、进程未起」，未在图中落定。

**建议**：在 §8.4 生命周期图中补 `starting → orphaned`（claim 已落但进程不存在）分支，或在图下加一行文字说明「`starting` 亦可直接判 `orphaned`，见 §10.1 矩阵第 3 行」。

### M4 · P3：认证投影增量更新与校准写入的事务关系未声明

**位置**：§8.5 认证投影表「时效」行（第 446 行）。

文本说「投影随校准写入增量更新；有效策略在每次 Gate 输入组装时读取当前认证快照」。但未声明投影更新是否与校准写入在同一事务内。§6.3 的事务纪律要求「耗时 IO 不得持有事务」并规定了事务内的四件事——投影更新属于哪一件（预算/游标/幂等记录？）没有交代。

若投影更新与校准写入不在同事务，存在「校准已写、投影未更新」的窗口。此窗口不致命（下一次 Gate 输入组装仍会读到最新投影，且 certification_version 变化会令旧缓存失效），但与 §6.3 的事务纪律应显式对齐。

**建议**：在 §8.5 或 §6.3 补一句：认证投影的增量更新在校准写入的同一事务内完成（属于「预算 / 游标 / 幂等记录」一类）。

### M5 · P3：§8.4 未声明 `.sift/context.md` 的读取源

**位置**：§8.4（第 411 行，策略从 base 分支读取）。

§8.4 明确声明策略（`policy.yaml`）从 base 分支读取（`git show <base>:.sift/policy.yaml`），但 `.sift/context.md`（PRD §5.7 的项目层 Context，注入 Task Spec）的读取源未声明。Context 与 Policy 同在 `.sift/` 下、同受默认硬护栏保护，但读取规则是否一致（从 base 读 vs 从 worktree 读）没有交代。

**影响有限**：`.sift/**` 是默认硬护栏，agent 修改 context.md 会在 Gate 被拦截；且 Task Spec 内容对 agent 行为的影响远不如 agent 自身的代码执行能力。但 Context 直接注入 LLM 提示词（Task Spec → Brain），若从 worktree 读取，agent 可修改 context 注入内容到自己的提示词——虽不构成门禁绕过（hard guardrail 仍拦），但属于 prompt injection 的间接通路，与 TM1 的防御纵深相关。

**建议**：在 §8.4 或 §8.3 补一句 Context 的读取源。若与策略一致（从 base 读），一行即可；若有理由从 worktree 读（如需反映最新 context），则声明该选择及其与 TM1 的关系。

## 4. 确认无问题的重要承接（抽查）

为避免只报问题，以下关键承接点本轮逐一核对过原文，确认成立：

- **PRD §13.1 五条已拍板约束**全部只展开未重议，逐条与 PRD V0.3 现行文本对账无误。
- **§14.3 已回写 PRD 的修订**四条全部在 PRD V0.3 现行文本中落定（§5.8 `sift report` CLI、§5.2 星号脚注、§12 #13/#15 结案标记、§4.1 `done` 语义裁决）。
- **§6.4 逐类副作用幂等协议表**逻辑自洽：可查远端证据的四类（打标、评论、创建 Change、合并）effectively-once 论证成立；Channel 推送如实降级为至少一次；agent 启动靠 claim 互斥而非幂等收敛，且被正确标识为表中唯一需要互斥的类别。
- **§10.1 恢复矩阵**的「进程身份不能只比 PID」纪律（组合启动时间 + 可执行路径 + control nonce）与「进程身份无法确认时不发信号」纪律，均为正确的事前安全选择。
- **§9.1 TM6 处置**的三条实现约束（`unsafe-local` 如实命名、星号只指 forge 侧、凭证 spike 作为证伪条件）与 ADR-007 一致；证伪条件是真正的证伪条件（若首批 agent 全为 keychain-only，方向在起点即不成立）。
- **§8.7 Attention 单一发射器**将配额记账、critical 熔断、severity 纯函数、结构校验全收敛在一个入口，且 severity 函数签名不接受升级请求（只接受降级），「凡能解除约束的字段必须确定性」靠类型系统而非自觉保证。
- **§8.8 Command** 的「标签路径与评论路径共用同一鉴权与幂等实现」是正确的 DRY 选择，避免了 PRD §9.2 要求的统一规则在实现中变成两处相似代码。
- **V10 测试**的写法（V0 断言「暴露面被诊断报告」，沙箱落地后翻转为「访问必须失败」）是优秀的工程实践——测试本身成为收口进度的刻度。
- **§13 交付切片**第 4 片的五项同片（Gate + 影子门禁 + 认证投影 + 回放集导出 + Change 创建）是 PRD §10.3 的排期表达，逻辑自洽。
