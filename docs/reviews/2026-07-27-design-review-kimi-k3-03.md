## 1. 结论

**技术栈重议本身合格，予以确认；但 D0.4 未处置 review-09 的任何一项 P1，整体维持 review-09 的阻断——在 R9-F1 / R9-F2 关闭前，不建议进入 WBS 或实现。**

D0.4 的实质变更只有一件事：技术栈切换 Go（ADR-009 取代 ADR-001），以及 PRD V0.4 新增分发/多平台非功能需求的配套更新。这部分逐点验证合格（§2）。但 attempt 启动协议——即 §8.4 两次同凭据 `claim:confirm`、§10.1 恢复矩阵、§8.4 关于 `running` 的论证——**与 D0.3 逐字相同**，review-09 指出的两个结构性失败面原样保留在文档里。技术栈可以换，协议缺陷不会因此消失；相反，Go 切换改写了 §5/§11/§14.7 却绕开了同一份文档里已被标记为阻断的 §8.4，这个优先级本身值得记录。

另需如实认账一点：review-09 R9-F1 所依赖的「同代双 wrapper 交错」证明，推翻的是我（review-08）把 confirm 可区分性判为「spec 接缝（P3，W3）」的结论。我在 D0.3 评审时独立推演过同代重复的可能性，但用「恢复路径已递增代次」把它降级了；review-09 用「读后立即 unlink 不是互斥原语 + worker 会话内双发」补齐了可达路径，这个升级是对的，我判轻了。

## 4. 本轮新发现

### N1 · P3：PRD 与 ADR-009 之间关于「为什么分发」的循环引用

**位置**：PRD §2.1 / §9.3、ADR-009 文首。

PRD 说分发需求的「理由见 ADR-009」，ADR-009 说推翻 ADR-001 的触发是「PRD V0.4 新增需求」。产品级「为什么现在要对外分发」的真实理由（迁移成本不对称：现在换是三处文档，有实现后换是全部实现且无渐进路径）目前只写在 ADR 里。按项目「事实只写一次，其余地方链接」的约定，**需求的理由应留在 PRD，ADR 链接回去**；现状是两个文档互相把对方当作出处，后续回溯时会找不到第一因。建议在 PRD §9.3 分发行补一句动机，ADR-009 改为引用。

## 5. 给 R9-F1 / R9-F2 的处置方向（供作者参考，非新发现）

按 DESIGN 自己「结构性保证优先于操作纪律」的标准，这两项应正式修订而非降级为 spec 接缝：

1. **两动词拆名或绑定会话 ID**：第二次确认携带第一次握手签发的、只属于该 wrapper 会话的 ID；pre-spawn 许可以 CAS 一次性消费，重复调用语义明示。
2. **worker 认领语义补进 §6.4**：启动 operation 必须有 daemon 会话内的原子认领/lease，不能把互斥责任推给预建 claim。
3. **Run → `running` 改以 `claim:started` 为准**：spawn 成功 + agent 子进程身份原子落盘后才推进；`control.json` 区分 wrapper PID 与 agent PID。恢复矩阵补「许可已发未 spawn」「spawn 已成、started 未落库」两行。
4. **线性化方案三选一**（review-09 已列）：我倾向「`spawning` handoff——claim 换代在发出 spawn 许可后冻结，直到收到启动证据或证实旧 wrapper 死亡」。理由是它复用现有 `run.sock` 通道与 fencing 代次，不引入 daemon 直接 spawn 的权限放大，也不要求跨平台 OS 级互斥原语——与 Go 切换后的多平台分发目标兼容最好。
5. 处置时建议增设 §14.8 对账节，记录 review-09 与本轮的处置映射。

## 6. 复评通过条件

沿用 review-09 §5 的五条，并补充：

1. 启动协议给出唯一、可线性化的 spawn 权；同代重复 wrapper、RPC 重试与 claim 换代均不能双起或零启动（R9-F1）。
2. Run 只在有可验证的 Agent 已启动证据后进入 `running`；恢复矩阵覆盖许可与真实 spawn 两侧的崩溃窗口（R9-F2）。
3. V2/V4 把上述竞态写成确定性交错测试。
4. Brain trace 采用独立调用身份，`gate_input_snapshot_id` 只在存在真实 Gate 关联时使用（R9-F3）。
5. README 1200 行阈值变更留下理由（R9-F5）；PRD 补充分发需求动机、消除与 ADR-009 的循环引用（N1）。

技术栈（Go）不再列为复评项——ADR-009 已关闭该话题。
