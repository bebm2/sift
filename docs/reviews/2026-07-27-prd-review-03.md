## 我新揪出的（按该处理程度排序）

### Gap A（最该处理，load-bearing）— §5.2 最小动词集 缺 actor 解析动词，但 §9.2 强依赖它
§9.2 说「轮询看到的是标签当前状态，不是谁改的，必须经 events/timeline 接口回溯 actor；取不到就当没发生」。但 §5.2 的最小动词集 11 个动词里，**没有任何一个负责解析「谁触发的这个事件」**。§9.2 是威胁模型的核心闸门，它依赖的能力在动词契约里是隐式的。

**修法**：动词集补一个 `getEventActor(kind, id, since)`（或把 actor 解析作为 `listIssueComments` / `listChangeComments` 的返回字段显式声明）。否则实现阶段会发现「我要的闸门，抽象层没给我铲子」。

### Gap B — §4.5 反向同步 的驱动性事件未显式挂 §9.2 actor 鉴权
§4.5 列了「触发标签被移除 → 终止」「Change 被手动合并/关闭 → 收敛」。这些显然是驱动性事件（能改 Run 状态），按 §9.2 必须 actor 校验。但 §4.5 没写。后果：一个非 allowlist 的人移除触发标签，就能静默杀掉一个正在跑的 Run；手动关 Change 的人若不在 allowlist，是否该收敛也没说清。

**修法**：§4.5 每条加一句「经 §9.2 actor 校验，actor 不在 allowlist 则忽略」。和 Gap A 同源，一起修。

### Gap C — §5.5 「critical 不占配额」无上限
critical 不占配额是合理的（不能因配额把真事故挡在外面），§11 `asleep` 也只放 critical 越过。但这意味着 **critical 是唯一不受配额约束的通道，且对 critical 本身没有任何速率/数量兜底**。极端情况下（比如一轮 CI 配置事故触发一连串 critical `guardrail_violation`），人会被 critical 洪水淹没，而配额机制完全无感。

**修法（V0 可接受，但 DESIGN 要记一笔）**：critical 不计入日配额，但建议加一条「critical 速率观察 + 单 Run/单窗口 critical 数熔断转 HITL」的可观测项，放进 §9.3 或 DESIGN。不阻塞 V0.2。

### Gap D — PRD/DESIGN 边界开始模糊
§5.2「优先用 `api` plumbing 子命令」、§9.2「经 events/timeline 接口」、§9.3「倾向 Bun + TypeScript 单进程」、§12 #12 技术栈——这些是**实现决策**，已写进一份声明「技术设计另文跟进」的需求文档。§13 文档卫生 callout 意识到了（callout 是设计理由不是 changelog），但没解决「已固化的实现选择该放哪」。

**修法**：把已拍板的技术约束（plumbing verbs、从 base 读策略、Bun+TS 倾向）在 PRD 里明确标注为「已采纳的架构约束 / 待 DESIGN 展开」，或直接在 §13 开一列「已下沉到 DESIGN 的决策」，避免 V1.0 时 PRD 和 DESIGN 重复且可能漂移。

### Gap E（小，但违反红线风险）— §11 `sift speak` 应拒绝 `min_modality: visual`
§11 永久红线是 `visual`（含全部 `code_review`）永不语音放行。但 §7.2 的 `sift speak <run>` 只说「用系统 TTS 朗读 Interrupt」，没说遇到 `visual` Interrupt 要拒绝。若实现时 `sift speak` 无差别朗读，就等于给 `code_review` 开了语音通道，踩红线。

**修法**：§7.2 / §11 显式写「`sift speak` 遇 `min_modality: visual` 直接拒绝并提示改文字/视觉渠道」。

### 一个行文小拧（非阻塞）
§5.3 第 374 行「token 耗尽会让 T6 退回『立即打断』的兜底」与第 377 行「token 超限时 T6 的兜底不是无差别立即打断、而是按 severity 阈值打断」表面冲突。374 是「若不处理会怎样」的动机句，377 是「我们定义的兜底」。建议把 374 的「立即打断」改成「（若不做 377 的约束）会退化成无差别打断」，避免读者误以为两条都在生效。
