# Sift PRD 追问：偏好/领域知识的积累，以及 HITL 的判定逻辑

> 针对问题：「Sift 如何积累用户的偏好和领域知识？或者说 Sift 是如何判定要不要 HITL？」
> 基于 PRD V0.2（2026-07-27）评审的第五轮追问。

---

## 一句话结论

**Sift 怎么判定要不要 HITL —— 写得很清楚，而且是设计对的地方。**
**Sift 怎么积累偏好和领域知识 —— 基本是空的，目前只有「证据账本 + 人写 context」两样东西。**

这两个问题表面上是一对，其实作者用一个很克制的原则把它们分开了：**HITL 永不由「学来的偏好」决定，学习只能进 policy、且只提案不生效。** 这恰恰是 A1 + 不对称阈值防火墙的正确推论，该给 credit。但「学习层」本身的缺失，是之前四轮没单独点出的真 gap。

---

## 一、Sift 怎么判定要不要 HITL（写得清楚）

HITL 的决定是一条**确定性规则树 + 一个风险分 + 一个证据门控的开关**，不是 ML 个性化。逐层拆：

1. **硬护栏命中 → 直接 `failed`，不进 HITL**（`§5.4`）。门禁自己裁定，连「要不要打扰人」都不需要判断。
2. **软护栏命中 → HITL `guardrail_violation`**（`§5.4`）。
3. **`review_policy` 决定要不要人审**：`always` / `risky-only` / `never`；其中 `risky-only` 由 **T3 风险评分**驱动（`§5.4` + `§5.3 T3`）。
4. **`auto_merge` 是最后一道开关，且被证据锁死**：只有「策略允许 + 门禁全绿 + 该类任务已通过影子门禁考核」才生效；证据未达标，配置里写了也不生效（`§5.4` + `§5.6`）。
5. **六类具体打断理由**已枚举（`§4.3`）：`design_approval`（T2 判高风险开工前）、`guardrail_violation`、`code_review`、`agent_blocked`、`merge_conflict`、`failure_review`，且各自钉死 `min_modality`（`code_review` 永远 `visual`，永不语音放行）。
6. **「要不要 HITL」和「什么时候 HITL」是分开的**：即便该打扰，也由 **T6 在注意力配额内调度**（`§5.5`），超额就合批降级，不是有事就喊。

关键：**T2/T3/T5 这些 LLM 触点只产出 recommendation（风险分、kind、agent、分诊），真正通断门禁、解析审批指令的，全是确定性代码（`§5.3`、`§7.1`）。** 这是 A1 的落地，不是口号。

> 所以「Sift 怎么判 HITL」的精确答案：**固定规则树（护栏→Checks→review 策略→auto_merge）+ T3 风险分（决定 risky-only 要不要人审）+ 影子门禁证据开关（决定 auto_merge 能不能开）+ T6 注意力预算调度（决定何时打断）。** 没有「它觉得你通常都会批」这种东西——而且故意不能有。

## 二、Sift 怎么积累偏好和领域知识（基本是空的）

把 PRD 里所有「Sift 从人身上学到东西」的入口扫一遍，只有三处，且都薄：

| 入口 | 位置 | 它真正做了什么 | 缺口 |
|------|------|----------------|------|
| **Context 文件** | `§5.7` | `~/.sift/context.md`（全局）+ `{repo}/.sift/context.md`（项目）+ 任务附注 + `/sift ask` | **人写、Agent 读**。Sift 不抽取、不更新、不归纳。「真相在仓库里，人写 Agent 读」——本质是手维护，不是积累 |
| **影子门禁记录** | `§5.6` | 记「Gate 预判 vs 人的实际决定、是否一致、Run 特征（kind/风险分/变更规模）」 | 只到**任务类型**粒度，用来过 §5.6 的阈值认证；没有「这个人倾向于拒绝碰 X 的变更」这种 per-decision 偏好 |
| **T7 校准提案** | `§5.3 T7` | 「从历史人工决策生成配置变更建议，**只提案不生效**」 | 唯一的学习触点，但只碰 **policy 阈值**（放宽 review_policy / 开 auto_merge），不碰偏好、不碰领域知识、不碰个别门 |
| **分派准确率** | `§10.2` | 追踪「T2 选的 agent 没被人改写的比例」 | 只是**观测指标**，没有任何写回 T2 的反馈环被描述 |

**结论：Sift 目前没有 per-user / per-repo 的偏好模型，也没有领域知识的语义抽取。** 「学习」目前只有两种形态：
- 聚合层的**政策校准**（shadow gate → T7 提案，且提案要人批、要过证据门槛）；
- 人肉维护的 **context.md**。

如果产品愿景里包含「调度器越用越懂你的口味、主动少打扰你」，那这一层现在**不存在**。

## 三、两个问题的关键张力（作者其实接住了，该给 credit）

你这问题最妙的地方在于：它逼出 Sift 一个**隐含但正确的设计选择**——

> **HITL 不能由「学来的偏好」决定。**

为什么？因为 §5.6 的防火墙是「**漏放是唯一致命指标**」。一旦允许「系统学了你通常都批，这次也替你批了」去跳过 HITL，就等于用个性化把漏放风险悄悄放大——一个你本来会拒的坏变更，因为「历史一致率高」被自动放行了。这直接击穿 §5.6 的双向不对称阈值。

所以作者现在的处理是自洽的：
- HITL 一律走确定性规则 + 风险分（第二节）；
- 学习只进 **policy 校准**（T7），而且**只提案、要人批、要过 shadow gate 证据门槛**（§5.6）；
- 学习**永不**去放松单条门禁或单条打断。

这条线是对的。我前面四轮没专门表扬，是因为它藏在一堆机制里不明显——但它是这份 PRD 在「AI 原生」这件事上没翻车的根。

## 四、我新揪出来的 gap：缺一个「校准账本层」

前面说「学习层基本是空」，具体空在哪、该补什么：

1. **决策特征太粗。** 影子门禁只记 `kind/风险分/变更规模`。要谈「懂你」，至少该记：触碰路径、文件类型、Issue 作者、时段、与历史相似决策的关联。现在连做 per-repo 偏好聚类的数据都不够。
2. **没有语义记忆抽取。** 人每次 reject/approve 的理由（尤其 `/sift reject <原因>` 带的自然语言）现在不进任何知识库；context.md 永远靠人想起去写。Sift 明明坐在最丰富的「人如何决策」的数据源上，却不用。
3. **T2 分派准确率无反馈环。** §10.2 追踪它，但没说「被改写后怎么反哺 T2 的下次分派」。观测了不学习，等于白采。
4. **T7 只碰 policy，碰不到 context。** 最自然的学习产物其实是：「你连拒了 5 个碰 `migrations/` 的变更，要不要我把这条加进项目护栏？」——把观察变成**人批的 context 草稿**，既 A1 合规（最终还是人写进 context），又把「积累」真正转起来。

**建议补的「校准账本层」四条原则（写进 PRD 即可，不必 V0 实现）：**
- 账本记录每次决策的**富特征**（不只是任务类型粒度）；
- T7 提案分两类：**policy 提案**（现有）+ **context 草稿提案**（新增，人审后落 context.md）；
- **防火墙不可越**：账本永远只能驱动「聚合 policy / 人审 context」，绝不允许用来放松单条门禁或单条 HITL；
- 明确一句话原则：**「Sift 积累的是可审计的校准证据，不是替人做主的口味模型。」** 这句话现在 PRD 里没写，但它是 A1 在「学习」维度上的必然延伸。

## 五、实战场景：agent_blocked +「记住，以后别问了」

用一Concrete 场景验证上面这套判断（用户原问）：Agent 处理任务时遇阻断 → 主动沟通澄清 → Human 告知处理方法并说「记住这个，以后别问了」。判定如下。

### 5.1 范围判定：一半在，一半不在

**「遇阻断 → 沟通澄清 → Human 告知如何处理 → 继续」—— ✅ 在范围内，一等公民。**
- `agent_blocked` 是 §4.3 明确列出的 6 类 HITL 理由之一，`min_modality: voice`（只分诊）。
- `/sift ask <文本>`（§7.1）：「注入澄清到 Task Spec 并继续」。
- §11 阶段 3 还预留了「口述澄清注入 Task Spec」的语音路线。
→ 这个闭环 V0 就该有。

**「Human 让他记住，以后别问了」—— ⚠️ 半个在，半个不在。**
- **容器在，机制不在**：存知识的去处是 `{repo}/.sift/context.md`（项目级）或 `~/.sift/context.md`（全局级），§5.7 已有；但 PRD **没有**「把一次澄清提升成持久 context」的命令。
- **`/sift ask` 只注入 Task Spec，不进持久 context**：§5.7 的 Context 分层表把 `/sift ask` 明确放在**任务层**（与项目层、全局层是分开的三档）。也就是说 Human 这次答的处理方法**只活在当前这一个 Run**，下一任务看不到。
- **架构上 Agent 无持久记忆**：每 Run 是「全新 worktree + 全新 Agent 进程」（§5.1 / §9.1 A5），Agent 跑完即死，不可能「自己记住」。所有「记忆」只能落在人写的 context.md。
- **「自动识别同类、主动不问」需要学习层**：这正是第四节说的 §5.9 缺失项，现在不存在。

### 5.2 必须亮红线

「以后不要再问了」若做成「Agent 学会了就自动跳过 `agent_blocked`」，**踩了第四节的 §5.9 防火墙**——`agent_blocked` 是一条 HITL，让系统基于「历史一致率高」自动抑制它，等于用个性化放大漏放风险（一个你本来会拦的真阻断，因「以前都这么处理」被静默跳过）。这跟「HITL 永不由学来的偏好决定」是同一根红线。

**正确做法**：Human 说「记住」→ 这条处理方法作为**人审后的 context 草稿**落进 `{repo}/.sift/context.md`（人写 Agent 读，符合 A1）→ 未来 Run 注入后 Agent 大概率不再撞同一阻断；但「要不要问」的最终裁定仍走确定性规则，不由 Agent 自拍板。

### 5.3 作者决定：暂缓机制设计

用户确认此场景后续可扩展，但**机制设计推迟到该阶段再定**，不在 V0 过度设计。届时三个子决策（路标已留）：
1. **提升触发器**：显式命令（`/sift remember`）还是 T7 自动提案（§5.9 的「context 草稿提案」，人审落盘）——倾向后者，符合「只提案不生效」。
2. **作用域选择器**：这条处理方法进**项目级**还是**全局级** context，依据「问题是否跨仓库通用」，需默认 + 人可覆盖。
3. **存储形态**：纯文本塞进 context.md，还是结构化「resolution 记录」（带触发条件，未来可检索复用）——后者决定能否做「自动识别同类不再问」。

> 这个场景本身就是第四节「该补 §5.9 校准账本层」最硬的理由：**最有价值的学习产物，是把一次 Human 澄清变成可复用的 context 草稿（T7 提案、人审后落盘），而不是让 Agent 偷偷学会跳过打断。**

## 六、一句话送作者

你的 HITL 判定逻辑是这份 PRD 最站得住的部分之一，别动。但「Sift 如何积累偏好与领域知识」这个问题，现在诚实的回答是「基本不积累，靠人写 context + shadow gate 攒证据」。如果产品名里的「注意力调度」要升级成「越用越懂你」，缺的不是机制，是一句被写下来的**学习层原则 + 一个富特征账本**。把它补成 §5.9，前四轮我揪的 A/B 承重墙问题都不如这一条影响产品灵魂。
