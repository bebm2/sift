## 1. 结论

**通过。建议进入 WBS 拆解与 specs 编写。**

D0.2 对上轮全部 6 个既有发现（F1–F6）、3 个新发现（N1–N3）以及 review-01 的四条建议均做了实质处置，无一驳回、无一敷衍。其中 F1、F2 走了复评条件允许的「如实声明」分支而非假装闭合——Q5 收窄为逐类投递语义、Q7 新增为质量场景、V10 用例锁定「暴露面必须被诊断报告」，这是本评审认可的处理方式。PRD V0.3 的 `done` 语义裁决（事实优先 + `gate_bypassed` 属性）干净地解开了 F6 的三方冲突，且未叠第二套状态机。

本轮新发现 1 个 P2 与 4 个 P3，均为修订引入的接缝与措辞问题，**不阻断**进入下一阶段，但 P2（M1）涉及 ADR-008 核心论证的一处裂缝，建议在写 `specs/control-plane.md` 前修正。

## 3. 本轮新发现

### M1 · P2：ADR-008「沙箱一挂即闭合」的论证与 run token 落盘位置冲突

**位置**：§3.2（约第 105 行）、§8.9（约第 503 行）、§9.1 TM6 表（约第 569 行）、ADR-008 §理由。

§3.2 与 ADR-008 把端点分离的价值论证为「沙箱只挂 `run.sock`、deny read `~/.sift/`，运维面即自然不可达」。但 §8.9 规定 run token 存放在 `~/.sift/runs/<run_id>/control.json`（0600），由 `sift report` 读取——deny read `~/.sift/` 之后，agent 连 token 都读不到，**上报面与运维面一起被关掉了**。也就是说，按当前文本的字面挂载集，沙箱关掉的不只是运维面。

**影响**：不影响 V0（无沙箱），但 ADR-008 正是靠这个论证把端点分离放进第 1 片的；论证有一处裂缝，而它是该决策的核心收益。未来落地沙箱时若按字面执行，会「闭合」出一个上报不可用的系统。

**建议**（任选其一，改动都很小）：在 §3.2 / §9.1 / ADR-008 把沙箱挂载集写全——「挂 `run.sock` + 该 Run 的 run dir（只读），deny 其余 `~/.sift/`」；或把 `control.json` 的落盘位置移出 `~/.sift/`（如 worktree 旁的独立目录）。这与 §9.1 已有的「`sandbox-clone` 后端」规划不冲突，只需补一句。

### M2 · P3：§7 目录树与 §11 未跟上双 socket

§7 的 `~/.sift/` 目录树仍只有 `siftd.sock`，缺 `run.sock` 与 `operator.token`；§11 仍写「控制面是属主 only 的 Unix socket」（单数）。两处都是 §3.2 修订的漏网。

### M3 · P3：§3.3 mermaid 图仍是单 socket 控制面

图中 `Sock[[Unix socket 控制面]] --> Engine` 且 `Ag -->|sift report| Sock`，暗示 agent 与人共用同一端点，与 §3.2 直接矛盾。图是代理实现时的高权重上下文，建议画出两个端点。

### M4 · P3：§14.4 Gate 形态行的缓存键是旧版

该行仍写「缓存键含 head SHA / gate 版本 / policy blob hash」，而 §6.5 已改为 `(run_id, head_sha, gate_version, effective_policy_hash, certification_version)`。§14.4 是分歧仲裁的历史记录，但记录的「本文结论」部分应与现行结论一致，否则两处缓存键并存。

### M5 · P3：README 行数阈值与 DESIGN §15 互相打架，另有两处 README 误伤

- README 本次把拆分阈值从「约 300 行」改为「约 1200 行」——818 行的 DESIGN 因此不再超限，但 DESIGN §15 仍写「本文超过 docs/README.md 建议的单文件行数上限」。两处必改其一。另外 300→1200 是 4 倍放宽，看起来是为容纳本文档而改规则；若确为有意决策，建议在 README 或 CHANGELOG 留一句理由，否则后来的文档失去拆分信号。
- README「各目录定位」表中 **`reviews/` 行被误删**（修订 `analysis/` 行时整行替换），`drafts/` 进了目录树却没进定位表。reviews/ 的命名与文件头约定仍在下文，属表格漏行。
