## 1. 结论

**维持 review-02 的结论：当前版本不建议进入 WBS 拆解或实现。**

经逐条比对，**DESIGN.md 自前两轮评审以来未做任何修订**（文件最后修改早于两份评审的写入时间），review-02 的 4 个阻断级问题（F1–F4）与 2 个重要问题（F5、F6）在当前文本中全部原样存在，无一关闭。

本轮独立阅读另发现 3 个新问题（N1–N3），均为 P2/P3 级，不阻断，但 N1 涉及对 PRD §3.4 取证节奏承诺的表述失真，应与 F1–F6 一并修订。

另需指出：review-01 给出「通过 / 优秀」、review-02 给出「不建议进入 WBS」，两份结论并存。本轮评审认为 review-02 的 F1–F4 论证成立（见 §2 复核），其结论优先；review-01 的肯定性评价对架构方向的判断依然有效，但其 §3 的四点微调建议中，§3.2（`SIFT_RUN_TOKEN` 环境变量暴露）已被 DESIGN §9.1「进程环境窥探：未闭合」如实吸收，其余三条（tick 解耦、影子快照同事务、doctor 退出码）属 specs 阶段事项，不留存量问题。

## 3. 本轮新发现

### N1 · P2：§13 首段「影子门禁记录器从第一片就存在」与切片表自相矛盾

**位置**：§13 首段与切片表，约第 553–563 行。

§13 首段声称「双平台骨架、**影子门禁记录器**、事件流从第一片就存在」，但切片表第 1 片只有「SQLite + 状态机 + 事件/outbox + fake Forge/Agent」，影子门禁首次出现是在第 4 片（「Gate + 影子门禁 + 回放集导出 + Change 创建，四者同片」）。

且这不是措辞瑕疵而是**结构必然**：§8.5 规定影子门禁记录器挂在 Gate 调用点上，Gate 第 4 片才存在，记录器不可能先于 Gate 存在。PRD §3.4 的「第一天就开始记录」的真实含义是「Gate 上线之日即常驻、无开关」（§8.5 的「每次调用都记，无开关」已正确承接），而不是「从代码第一片开始记录」。

**影响**：首段表述会给 WBS 拆解传递错误约束（第 1 片就要带影子门禁），与 PRD §10.3「回放集与 Gate 同期」的正确承接（第 4 片四者同片）打架。

**建议**：删去首段中「影子门禁记录器」，改为「双平台骨架与事件流从第一片就存在；影子门禁记录器随 Gate 于第 4 片落地并自此常驻无开关（PRD §3.4 / §10.3）」。

### N2 · P3：§6.1「每个 tick 执行一步转移」与多阶段派发、多 Run 并发的吞吐语义未定义

**位置**：§6.1，约第 193–201 行。

同一段先写「每个 tick 做同一件事——读取……计算差量，**执行一步转移**，落库，结束」，随后又说「tick 按优先级派发：intake 轮询 → 反向同步 → Checks 跟进 → HITL 超时与升级扫描 → 重试退避 → outbox 推进」。两处描述的每 tick 工作量不一致：前者是每 tick 一步转移，后者是每 tick 扫完六个阶段。

更重要的是：若字面取「一步转移 / tick」，则在 ≥3 Run 并发（Q4 的验收场景）下，Run 间的转移吞吐与轮询间隔（10–60s）直接耦合——一个 tick 只能推进一个 Run 的一步，其余 Run 的 HITL 超时、Checks 跟进都要排队等下一个 tick，最坏延迟 = Run 数 × tick 间隔。这与 PRD §9.3「打标 → Agent 启动 P50 < 60s」在非空闲状态下可能冲突。

**建议**：明确每 tick 的语义为「每个优先级阶段内，对所有待处理的 Run / outbox 项各执行一步（或有界 N 步）」，把「一步」的粒度从「每 tick 全局一步」澄清为「每阶段每对象一步」，并在 V8 预算/负载测试中覆盖多 Run 并发下的推进延迟。此条与 F5（阶段间饥饿）互补：F5 管类别公平，本条管吞吐语义。

### N3 · P3：「备用通道告警」与 V0 单 Channel 决定的接缝未定义

**位置**：§6.4 末段（约第 238 行）、§14.2 #7、PRD §7.3。

§6.4 要求「推送失败不改变 Run 已进入 `waiting_human` 的事实，但必须持续重试并在**备用通道**告警——否则一个静默失败的 Interrupt 等于把 Run 挂死」。这个防护方向正确，但 PRD §7.3 明确「V0 只实现一个 Channel」，且 Channel 具体实现未定（§14.2 #7 保持开放）。在单 Channel 的 V0 里，「备用通道」是什么没有答案：它既不是一个已存在的模块，也不在任何交付切片里（§13 第 5 片只有「首个 Channel」）。

**影响**：「Interrupt 静默失败挂死 Run」的防护在 V0 可能落空——不是没有机制，而是机制引用了一个不存在的部件。

**建议**：在 §6.4 或 §8.7 明确 V0 的兜底告警路径。低成本候选：forge 决策简报评论本身就是与 Channel 独立的第二渲染面（§8.7 renderer 已区分两者），可规定「Channel 推送失败 N 次后，以高优先级 outbox operation 在对应 Issue / Change 下发告警评论，并在 `sift ps` / `sift doctor` 中标记推送故障」。如此「备用通道」在 V0 内闭合，且不依赖 #7 的裁决。

## 4. 确认无问题的重要承接（抽查）

为避免评审只报问题，以下关键承接点本轮逐一核对过原文，确认成立：

- **PRD §13.1 五条已拍板约束**全部只展开未重议：plumbing 集成（§8.1）、Sift 创建 Change（§8.4）、策略从 base 读且「无读 worktree 策略的函数」（§8.4）、actor 回溯 fail closed 类型化（§8.1）、敏感配置启动期读入（§9.1）。
- **§14.3 回写对账属实**：PRD §5.8 已改为 `sift report` CLI、§5.2「零凭证管理」星号与 TM6 脚注、§12 #13 / #15 结案标记均在 PRD 现行文本中，两份文档此三处无漂移。
- **A7 防火墙**在 §8.6 的表述（账本无流向 Gate / Attention 的路径）本身正确——F3 的问题不在防火墙，而在 `auto_merge` 证据门槛没有合法的聚合消费者，两者需要靠「认证投影」同时满足，而非牺牲防火墙。
- **TM6 三条实现约束**（`unsafe-local` 如实命名、星号只指 forge 侧、凭证 spike 作为证伪条件）与 ADR-007 一致，态度与表述均无过度声明。

## 5. 修订建议顺序（合并 review-02 §4）

1. **F6 先行**：回 PRD 裁决手工合并与 `done` / Gate 不变量的语义冲突（DESIGN 无权单方面选择）；
2. **F1**：定义 socket RPC 的服务端授权模型，或如实把控制面列入 TM6 未闭合清单并修订「Layer 1 永不越权」的表述；
3. **F2 + F4 联合**：逐类副作用幂等协议 + attempt 生命周期建模 + 恢复矩阵补行；
4. **F3**：认证投影（Ledger 的合法聚合消费者）+ 认证版本入缓存键与回放证据；
5. **F5 + N2**：outbox 公平调度规则与每 tick 吞吐语义，一并进 V8；
6. **N1 + N3**：措辞与接缝修正，随上述修订同批完成；
7. 同步检查 ADR-003 / 005 / 006 是否需追加替代 ADR（review-02 已指出）。
