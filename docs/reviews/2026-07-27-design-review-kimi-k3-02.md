## 1. 结论

**通过。建议进入 WBS 拆解与 specs 编写。**

D0.3 对四份复评的发现全部做了机制级处置，无一驳回（R7-P1-3 为部分采纳，理由写明且成立）。尤其关键的是：**文档在结论分歧上做了正确的选择**——§14.6 明示采纳 review-05 的「暂不进 WBS」而非包括我在内的另三份的「通过」。复盘看，review-05 是对的：它的三个 P1（缓存键漏输入、claim 协议不可实现、Change 证据不唯一）都打在 D0.2 新机制的可实现性上，而我（review-06）与 review-04 核销的只是「修订文字是否出现」。这是评审方法论上值得记下的一笔：**文字核销 ≠ 机制验证**。

D0.3 的三处核心修订逐一验证成立（§3），未发现新的阻断项。本轮新发现 3 项，均为 P3 级接缝问题，不阻断进入 WBS，随 specs 阶段收敛即可。

## 3. 本轮新发现（均 P3，不阻断）

### W1 · P3：README 阈值放宽的理由仍未留存

R6-M5 的处置补了漏行、改了 §15，但「约 300 行 → 约 1200 行」这个 4 倍放宽本身没有在任何地方留下决策理由（README、CHANGELOG、§14.6 均无）。这条规则影响之后所有文档的拆分信号，而它目前看起来像是为容纳 DESIGN 而改。建议：若是有意决策，在 CHANGELOG 或 README 补一句理由（例如「阈值从『触发考虑拆分』重新定义为『必须拆分』」）；若是无意的，改回 300 并把 DESIGN 拆分。一行的事，但规则的来历应该可查。

### W2 · P3：§7「两类回放对象共用同一个 `gate_input_snapshot_id`」对非 Gate 触点不成立

§7 规定 Gate 输入快照与 Brain 触点 trace「两类共用同一个 `gate_input_snapshot_id` 关联」。但 T1（体检）、T2（分派）、T6（调度）、T7（提案）发生在没有任何 Gate 调用的时点，不存在可关联的快照 ID；即使是 T3，重试后也会有多个快照。按字面实现，这些 trace 要么悬空、要么被迫关联一个不属于它的快照。

**建议**：Brain trace 以 `(run_id, attempt_no, 触点, 调用序号)` 为主键，仅 Gate 相关触点（T3 及未来同类）额外携带 `gate_input_snapshot_id` 外键。`specs/storage.md` 写表结构时落实即可，DESIGN 改一句措辞。

### W3 · P3：两次 `claim:confirm` 的可区分性与 start operation 的会话内重复执行仍是隐含语义

§8.4 协议的正确性依赖两条目前只藏在字里行间的约束：

1. daemon 侧必须按 attempt 阶段区分两次 confirm——第一次仅在 `pending` 可接受，第二次仅在 `starting` 可接受。若实现成「凭据合法且代次匹配即接受」，则一个在 `starting` 阶段重复 confirm 的竞争 wrapper 与合法 wrapper 的第二次 confirm 无法区分（同 nonce、同代次）。
2. 「两个 wrapper 竞争」在 D0.3 模型下只剩一条路径：outbox worker 在**同一会话内**重复执行同一启动 operation（跨会话的重复已被恢复矩阵的代次递增挡住）。这要求 worker 对 operation 有认领/去重语义——§6.4 说 worker「至少一次」执行，这条恰恰对启动 operation 不成立（它是互斥类，不是幂等类）。表里有这句，但「worker 如何保证同一会话内不双发」没有承接点。

两者都不是设计缺口，是实现时一定会撞上的问题，而答案应该只有一个写法。**建议**：在 `specs/control-plane.md` 写明两次 confirm 的阶段前置条件（或直接拆成 `claim:confirm` / `claim:fence-check` 两个动词），并在 `specs/outbox.md` 写明启动类 operation 的 worker 认领语义。§15 两份 spec 的范围已涵盖，此处只登记，不要求改 DESIGN。

## 4. 确认无问题的重要承接（抽查）

- **ADR 同步质量**：003/004/005/006/008 的正文均与 D0.3 逐点一致，且各自保留了「D0.3 修订（评审编号）」的溯源注记——ADR 没有沦为只改标题的空壳。
- **fencing 协议的完备性**：恢复矩阵 12 行逐一推演（含「claim 已确认但进程不在」「旧 wrapper 苏醒」「多 wrapper 竞争」），每行收敛动作唯一确定，且递增代次与释放同事务——D0.2 那个「恢复动作自身引入双起」的漏洞确实堵上了。
- **§14.6 的编号警示**（两套 M1–M5、两个「第 4 轮」）与 README 新增的「序号一经占用不得复用」规则，正是 04/07 撞车事件的正确沉淀。
- **§13 补充**（`run.sock` 凭据决定动词子集须在第 1 片定形）是有前瞻性的排期约束，避免了第 3 片返工鉴权层。
- **§14.6 新增的两条维护义务**（快照即输入全集、fencing 单点递增）与 §14.5 的两条同类，均为「结构保证退化为纪律保证」的风险点——建议带进 WBS 验收。
