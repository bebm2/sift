# WBS.md 评审（第 1 轮）

> 日期：2026-07-28
> 评审对象：[`docs/WBS.md`](../WBS.md) **D0.1**（对应 DESIGN D0.10 / PRD V0.8）
> 评审依据：[`docs/PRD.md`](../PRD.md) V0.8、[`docs/DESIGN.md`](../DESIGN.md) D0.10、[`docs/README.md`](../README.md)、active ADR 001–013、[review-18](2026-07-28-design-review-kimi-k3-06.md)
> 评审范围：WBS 与 PRD §10.1（PoC 成功标准）、DESIGN §13（交付切片）的全面对照；硬约束 H1–H15、V1–V15 门禁汇总、A1–A10 人工验收的完整性与一致性；里程碑验收标准表的完备性

## 1. 结论

**WBS 的骨架质量很高：八片切片与 DESIGN §13 严格对应，硬约束 H1–H15 可追溯，V1–V15 与 A1–A10 覆盖完整，文档前置检查正确承接了 review-18 的非阻断遗留。** 但存在一项阻断级问题：**Brain 模块（T1–T7 触点 + 统一调用壳 + `specs/brain.md`）在全部八个里程碑中无任何任务分解与 spec 落点**，而它是 PRD §3.1 端到端流程的必经环节，且 DESIGN §8.3 / §15 已给出实质设计与明确的派生文档。此问题不闭合，M1 的"分派"闭环与 M5 的 token 预算收费口均缺少可实现落点。

本轮发现 6 项：W1（P1，阻断）、W2–W4（P2）、W5–W6（P3）。

值得肯定的是：WBS 对 DESIGN §13 八片的展开忠实且无新增设计决策；硬约束表（H1–H15）逐条标注来源、未夹带私货；文档前置检查把 ADR-010 改名动作正确地放在"第 1 片启动前"并配了可执行的验收条件（"搜索结果不在历史/指针中的每处旧名各计一条 blocking bug"）；全局风险管理表覆盖了 `modernc.org/sqlite`、平台差异、凭证 spike 等关键风险。这些是 WBS 作为"可执行工作分解"的合格底座。

## 2. 阻断级发现

### W1 · P1：Brain 模块（T1–T7 触点 + 统一调用壳 + `specs/brain.md`）系统性缺位

**位置**：WBS 全文 M1–M8。

WBS 全文仅 5 处提及 Brain / 触点，全部是**引用或约束**，没有一处是实现任务：

| 行 | 内容 | 性质 |
|----|------|------|
| 416 | Gate 判定顺序中"T5 分诊" | 流程描述 |
| 421 | "风险评分（T3）作为输入传入，Gate 不调用 Brain" | Gate 任务的一条约束 |
| 457 | 回放集含"Brain 触点 trace" | M4 回放集导出的数据项 |
| 541 | "每日 token 上限（Brain 调用壳收费）" | M5 预算的收费口声明 |
| 545 | "token → 全触点走确定性兜底" | M5 预算超限行为 |

对照之下，PRD 与 DESIGN 对 Brain 有明确的、不可省略的要求：

1. **PRD §3.1 流程第 2 步**："Brain：一次 LLM 分派 → 选定 Agent + Goals"——这是 M1 端到端骨架闭环（WBS §1.8）"Issue 摄入 → **分派** → 执行 → Gate → 合并"的必经环节。M1 用的是 fake Agent，但 WBS 未说明"分派"在 M1 是确定性 fake 还是真的接入 Brain 调用壳，也未说明真实调用壳何时落地。

2. **PRD §5.3** 定义了 T1–T7 七个触点，每个都有独立的职责、输出 schema、确定性兜底路径。DESIGN §8.3 给出了实质性设计：统一调用壳（`调用 → 经 decode gateway 校验 → 失败重试一次 → 再失败走兜底`）、提示词作为可版本化资产（同文件进 git）、token 记账白送（agent CLI JSON 输出含 usage）、输入经 stdin/临时文件传递。**这些不是 trivial 实现细节**——WBS 对同等粒度的模块（如 M3 wrapper 契约八条、M4 Gate 判定顺序、M5 Interrupt 发射器五件事同事务）都做了完整任务分解，唯独 Brain 没有。

3. **DESIGN §15 派生文档清单**明确列出 `specs/brain.md` 待写（"七个触点的输入/输出 schema、兜底表、提示词版本约定"）。WBS 各里程碑"需要先写的 spec"列表覆盖了 `storage.md`、`control-plane.md`、`config.md`、`outbox.md`、`forge.md`、`runtime.md`、`gate.md`、`ledger.md`、`policy.md`、`interrupt.md`、`command.md`、`report.md`——**唯独缺 `specs/brain.md`**。

**连锁影响**：
- M5 §5.5 的 token 预算收费口是"Brain 调用壳"，但调用壳无人实现——超限降级行为（"全触点走确定性兜底"）缺少载体。
- M4 §4.1 的 Gate 接入 `riskScore`，Gate 不调用 Brain（H3 纯函数约束），那 T3 的调用壳实现落在哪片？
- M4 §4.4 回放集要求导出"Brain 触点 trace（各触点的输入/输出、提示词与 schema 版本、是否走兜底）"，但触点调用身份 `(run_id, attempt_no, touchpoint, call_seq)` 的记录机制无人实现。

**建议**：在 WBS 中显式落点 Brain 模块。最小改动是新增一个任务组（建议并入 M2 或 M4，取决于首个真实触点的实现时点），至少覆盖：
- 统一调用壳实现（decode gateway 校验 → 重试 → 兜底，DESIGN §8.3）
- T1–T7 各触点的输入/输出 schema + 确定性兜底（PRD §5.3 表逐条）
- 提示词版本化资产管理（进 git，回放集记录版本）
- token 记账接入预算表
- `specs/brain.md` 加入对应里程碑的"需要先写的 spec"列表

同时在里程碑总览表中标注各触点的分散落点（如 T3 随 Gate 在 M4、T4/T6 随 Interrupt 在 M5、T1/T2 随 Intake/分派在 M2），避免实现者误以为 Brain 是一个独立切片。

## 3. P2 发现

### W2 · P2：里程碑验收标准表遗漏汇总表标注的 V 测试

**位置**：M1 验收标准表（WBS 行 184–193）、M2 验收标准表（行 283–290）vs 自动化门禁汇总表（行 745–762）。

各里程碑的验收标准表是该里程碑完成的判定依据，但与文末汇总表对不上：

| 遗漏项 | 汇总表标注 | 对应里程碑验收表 | 现状 |
|--------|-----------|-----------------|------|
| **V9**（端到端，fake 部分） | 切片 M1、M7；验收 M1 + M7 | M1 验收表（行 184–193） | M1 验收表列了 V1/V2/V10a/V10b/V14/V15，**未列 V9**；仅有一条"fake Forge/Agent 骨架闭环跑通（开发者本地手动验证）"与之近似但不等价 |
| **V11**（手工合并冲突） | 切片 M2；验收 M2 | M2 验收表（行 283–290） | M2 验收表只列 V3/V7，**未列 V11** |
| **V12**（零配置启动） | 切片 M1；验收 M1 | M1 验收表 | **未列 V12** |

验收标准表是 AI 代理与人类实现者判定"该里程碑是否完成"的唯一入口。汇总表在文末、验收表在每节首部，读者通常只看后者。遗漏会导致验收时漏项——尤其 V11（手工合并 → `done` + `gate_bypassed`）是 PRD §4.5 反向同步的核心断言，V12（零配置启动）是 DESIGN §14.2 对"所有开放数值都有确定性默认值"这条承诺的可验证性兜底。

**建议**：将 V9（fake 部分）/ V12 补入 M1 验收标准表；将 V11 补入 M2 验收标准表。或者在汇总表与验收表之间建立明确的交叉引用纪律（每条 V 在其主验收里程碑的表中必须出现）。

### W3 · P2：V5（Gate 安全测试）验收归属 M3，但核心断言需 Gate（M4）才能验证

**位置**：V5 汇总表（WBS 行 750）、M3 验收标准表（行 397）。

V5 在汇总表中标注"对应测试切片 M3 / 验收阶段 M3 验收"，M3 验收标准表也列了"`.sift/**` 硬护栏拦截 | V5"。但 V5 的断言内容是：

> `.sift/**`、CI 配置路径 **fail closed**；base vs worktree 读取

其中"base vs worktree 读取"（策略从 base 分支读取、无读 worktree 的函数）确实在 M3 §3.4 worktree 管理中实现，可在 M3 验收。但"`.sift/**`、CI 配置 fail closed"是 **Gate 硬护栏**的断言（PRD §5.4 / DESIGN §8.5），Gate 在 M4 才实现。M3 没有 Gate，无法测试硬护栏 fail closed 行为。

当前写法会让实现者在 M3 验收时面对一条无法通过的验收项，或在 M3 用临时桩绕过——两种都是 WBS 应避免的。

**建议**：V5 拆分为两部分标注归属——"base vs worktree 读取源"留在 M3 验收（可独立断言），"`.sift/**` / CI 配置 fail closed"移至 M4 验收（Gate 实现后）。或保持 V5 整体跨 M3–M4，但在 M3 验收表中注明"仅 base/worktree 读取源部分，硬护栏部分待 M4"。

### W4 · P2：A3（并发 PoC 标准）的真实并发验证落点不清

**位置**：人工验收汇总表（WBS 行 771）。

A3"≥3 Run 并行时打扰不突破注意力配额"标注"验收切片 M5 / 形式 V8 自动化断言"。V8 确实在 M5 验收（自动化模拟并发）。但 PRD §10.1 原文是：

> ≥3 个 Run 并行期间，打扰次数不突破注意力配额，且触及配额时确实降级为合批摘要

V8 自动化测试能证明**机制正确**（配额不被突破、超额降级），但"≥3 个 Run 真实并行"需要真实 Agent（M7 才具备）。M5 只有 fake Agent，其并发是模拟的。PRD §3.4 明确"打扰不淹没人只在并发场景显现"——这里强调的是**真实并发**。

当前标注把 A3 完全归到 M5，但 PoC 的真实并发验收记录应在 M7（与 A1/A2/A4 同属"一次性验收记录"）。M5 的 V8 断言与 M7 的真实并发验证是两件事，前者是自动化保证，后者是 PoC 证据。

**建议**：A3 的"形式"补充说明"V8 自动化断言（M5）+ 真实 ≥3 Run 并发验收记录（M7）"，或将其验收切片改为"M5（自动化）/ M7（PoC 验收）"，与 A1/A2/A4 的形式（一次性验收记录）对齐。

## 4. P3 发现

### W5 · P3：M4"影子门禁常驻无开关"仅以代码检视验收

**位置**：M4 验收标准表（WBS 行 479）。

WBS M4 验收："影子门禁常驻无开关 | 代码检视：无开关分支"。这对应硬约束 H4（DESIGN §8.5："影子门禁记录器挂在 Gate 调用点上，每次调用都记，无开关"）。但验收方式是"代码检视"，而 WBS 其他硬约束（如 H3 Gate 纯函数）都用 V6 自动化回放测试验证。

代码检视不是自动化门禁，在 CI 中不构成防线，且 WBS 文末汇总的 V1–V15 中没有一条覆盖影子门禁的"无开关常驻"。

**建议**：在 V6 Gate 回放测试中增加一条行为层断言——"每次 Gate 调用必须产生一条 `calibration` 行写入"，使得"无开关"从代码结构属性变为可执行的行为断言。这条断言能捕捉"有人加了一个 `if config.shadowEnabled` 分支"这类回归。

### W6 · P3：M7 §7.2 与 §7.5 内容重叠

**位置**：M7 §7.2 双平台 Forge 集成（WBS 行 630–636）与 §7.5 双平台低频验收链（行 655–657）。

§7.2 已包含"GitHub 真实项目全流程"和"GitLab 真实项目全流程"。§7.5 又单列"真实 GitHub 与 GitLab 各至少 1 次完整流程（§3.1 PoC 成功标准）"。两者任务内容重叠，且都对应人工验收 A2。实现者无法判断这是同一件事（§7.5 是 §7.2 的验收收口）还是两件独立的事。

**建议**：合并为一个任务组，或明确区分语义——例如 §7.2 标注为"开发期逐平台验证"，§7.5 标注为"PoC 正式验收记录（§3.1 成功标准）"。一条 inline 注释即可消歧。

## 5. 确认无问题的重要承接（抽查）

为避免只报问题，以下关键承接点逐一核对过原文，确认成立：

- **H1–H15 硬约束**逐条标注来源（PRD A1 / §13.1 / §5.4 / §9.2、DESIGN §6.2 / §6.4 / §8.4 / §8.5 / §13 / §14.2 / §14.14、ADR-011），未夹带 WBS 自创的设计决策，与 PRD §13.1 六条已拍板约束及 DESIGN 各处结论一致。
- **文档前置检查**正确承接 review-18 的非阻断遗留（ADR-010 决策 6 改名 `attempt_resolution`），动作（加修订指针不重写正文）、规范来源（V0 枚举 `reject | retry_after_absence`）、验收条件（旧名不在历史/指针中即计 blocking bug）与 DESIGN §14.14 完全一致，且遵守 ADR 只追加规则。
- **H5 同片不拆**（Gate + 影子门禁 + 认证投影 + 回放集 + Change 创建）正确映射到 M4，与 DESIGN §13 第 4 片及 PRD §10.3"回放集不得延后"一致。
- **H6/H7 提前到 M1**（控制面授权、CGO_ENABLED=0 交叉编译）与 DESIGN §13 的两条排期裁决（§13 末段两段说明）一致。
- **人工验收 A1–A10** 与 PRD §10.1 的 10 项 PoC 成功标准一一对应（闭环/双平台/并发/负样本/安全/门禁/注意力/多 Agent/恢复/发布），未遗漏也未新增。
- **M3 恢复矩阵**（§3.5）的 12 行恢复动作与 DESIGN §10.1 的启动期恢复矩阵逐行对应，"恢复先于 operation lease 回收"与 DESIGN §8.4 / §10.1 一致。
- **M3 wrapper 契约八条**（§3.1）与 DESIGN §8.4 八条逐条对应；spawn handoff 五步协议（§3.2）与 DESIGN §8.4 八步表对应（WBS 合并为五步描述，语义未丢）。
- **全局风险管理表**覆盖 `modernc.org/sqlite` 长生命周期正确性、平台差异迭代、凭证 spike keychain-only、tmux 依赖、注意力配额设计等关键风险，且每条配了缓解措施与影响面限定。
