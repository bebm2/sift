## 1. 结论

**通过。阻断解除，维持「可以进入 WBS」的判断。**

review-14 的 F1（P1）关闭方式是协议级的而非打补丁：单一 `attempt_decision` marker（CAS、不可逆）作为「迟到事实 vs 人的决定」的唯一线性化点——决定未提交前事实优先（同一事务推进 attempt + Run `waiting_human → running` + Interrupt 标 `superseded_by_fact` + 接管监督，807 行），决定已提交则由决定吸收事实（不推进 Run，但登记可终止身份、回 `superseded_by_decision`、继续执行终止，808 行）。第二行是这套设计真正的价值：迟到的 `started` 恰好携带确切 Agent 身份，把「证明不了」变成「可执行的终止」——810 行把这句话写进了文档，拒绝 RPC 而放任 Agent 存活被显式禁止。四个入口共享同一套 CAS 前置与幂等结果（812 行），这正是 V2/V4 能把交错写成确定性测试的前提。

我对人工态仲裁做了独立的交错重放（§4），未找到新的双写、幽灵状态或跨投影部分提交路径。本轮新发现两项 P3（§5）：一处仲裁边界上的措辞悬空、一条未声明的健壮性前提，均不阻断 WBS，建议在第 1 片开工前顺手修掉。

另认账一句：D0.7 未采纳我在 review-13 建议的「后端中性执行句柄」，改为裁决执行拓扑（agent 恒为 wrapper 直接子进程、恒在其进程组内）——这个方案比我的建议更小也更强，拒绝理由（按会话名探测正是 §8.4 开头拒绝依赖的东西）成立，我接受。

## 3. D0.7 拓扑裁决与我 review-13 遗留的复核

- **R13-N1（P2）：关闭，且方案优于我的建议。** 裁决为「后端只决定 wrapper 跑在哪里，永不插到 wrapper 与 agent 之间；agent 恒为 wrapper 直接子进程且恒在其进程组」（98、438、440）。观测原语因此构造性后端中性，恢复矩阵一行不改——比维护两套观测语义小。代价如实记录：真 PTY 改由 wrapper 自建中继，tmux 价值收窄为 attach 与持久宿主（443 行区域、ADR-005 同步）。连带修订正确：§3.2（98）、fd 下发理由（480，方向改为「后端夹在 siftd 与 wrapper **之间**之上」并加指向）、V4 增加「两个后端同一套断言 + tmux 下 agent 仍是 wrapper 直接子进程」的拓扑守卫断言（869）、第 6 片范围注明「不引入第二条证据链」（904）。
- **R13-N2（P3）：关闭。** §10.1 路径表（780–784）：恢复 → 按重试策略；`retry` → 新开 attempt；`kill` → 不新开、Run 转 `failed`（「人要求终止的任务不得被系统自动续命」）；§8.10 同步。V4 有「kill 后不得出现新 attempt、retry 后必须出现」的反向断言（869）。
- **D0.7 自查项（`running` 阶段 `orphaned` 纪律推广）：关闭。** 这是本族问题的第三次出现（§14.10 已自记），推广后「任一时刻至多一个存活 Agent 写该 worktree」在 `running` 阶段也闭合。

## 4. 人工态仲裁的独立对抗复查（通过项）

我重放了以下交错，均闭合：

- **started 与打扰事务竞争**：started 先落库则 attempt `spawning → running`、打扰生成前置失败不发；打扰先落库则按 807 行同一事务推进 + `superseded_by_fact`。V4 两组交错均覆盖（869）。
- **决定（retry）后迟到 started**：被吸收——登记可终止身份、wrapper 收 `superseded_by_decision` 自行终止 agent、继续受控终止，确认消失后才新开 attempt。这正是「人误报已在系统外处置」场景的保护网：新 attempt 开在旧执行体可能被错判消失之后，吸收规则兜住第二个写者。
- **决定（reject）后迟到 started**：同样被吸收并终止；Run 保持 `failed`，隔离标记独立存在，worktree 不回收不复用（795、799）——「终态 = 已停」的误读被 799 行显式禁止。
- **hold 不写 marker**：`hold` 不在 808 行的决定列内，事实窗口在 hold 期间保持开放——迟到的合法 started 仍能赢。方向正确（但见 N1 的措辞问题）。
- **并发发现者**：超时扫描 / 恢复扫描 / `kill` / `retry` 四路并发，生成键唯一约束保证一条 Interrupt、一次扣费、一条发布 operation（601、801、V4 869）。
- **隔离与重试的交互**：`failed → queued`（人工 retry）时新 attempt 不复用被隔离的 worktree（351 行隔离标记）；D0.7 拓扑保证「进程组消失 ⟺ agent 消失」，因此「确认消失后才新开」在操作系统层面可证。

## 5. 本轮新发现

### N1 · P3：仲裁表「人的决定」列里的「过期升级的处置」没有指称对象，措辞悬在 CAS 边界上

**位置**：§10.1 line 808。

808 行把写 `attempt_decision` 的一方列为「`retry` / `reject` / **过期升级的处置**」。但对 `startup_stall`，PRD §4.2（232 行）规定的过期路径是 `escalate` → 达上限落 `hold`，**不存在任何自动的终态处置**；而 `hold` 按 796 行与 808 行的结构都明确不是决定（不写 marker，事实窗口保持开放）。于是「过期升级的处置」指向不存在的东西。两种读法都有害：若实现把自动 `escalate` 当成写 marker 的时机，一个定时器就推翻了事实优先——迟到 started 会被吸收、合法启动的 agent 被终止，而全程没有人做过任何决定，这与 807 行的设计意图直接冲突；若实现忽略这个括号，则说明它本不该写。建议改为「仅 `retry` / `reject` 写 `attempt_decision`；`escalate` 与 `hold` 不写」，一句话即可，但因为它悬在仲裁的 CAS 前置上，应在 WBS 第 1 片开工前修掉。

### N2 · P3：消失证明依赖「agent 不主动脱离进程组」，此前提未声明

**位置**：§10.1 判定纪律、ADR-010。

D0.7 拓扑裁决使「进程组存在 ⟺ 有成员存活」成为整套终止与恢复证据的地基。但 Unix 下子进程可以 `setsid` / 二次 fork 脱离进程组——一旦脱离，「进程组已消失」为真而 agent 仍在写。V0 的 agent 是已知 CLI、威胁模型也不包含对抗性逃逸（TM6 本就未闭合），且这是所有 Unix 监督者共有的局限，不阻断 WBS。但§6.4 的不变式现在事实上多承载了一条未写出的假设，建议在 §10.1 判定纪律或 ADR-010 风险段补一句：「消失证明假设 agent 不主动脱离进程组；已知 agent CLI 无此行为，该假设随 agent 白名单（§8.4 未知 agent 名拒启）一并维护」。
